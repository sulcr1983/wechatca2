# 对抗性审查：更新记录方案（2026-11-03）

> 视角切换：换模型重做，**第一性原则 + 对抗性审查**。目标是推翻前面两份报告的结论，找更省事的解法。
> 方法：先立论「版本边界必须靠人手」，再用 git 历史实测去**证伪自己**。

## 0. 审查结论（先说最重要的）

**我昨天那句「版本边界必须靠人手，机器猜不出来」是错的。**

`git log -- pwa/version.json` 直接给出了**完整、精确、零人工**的版本时间线：

```
2026-10-18 13:57  v1.0.0    0332b7f
2026-10-19 04:48  v1.4.0    0f0f9c1
…
2026-10-31 21:10  v1.13.0   f5a0e4f
2026-10-31 22:01  v1.16.0   204c083   ← 注意：这里跳号了
2026-10-31 22:11  v1.16.1   33a440d
2026-11-01 10:47  v1.17.0   2d844cc
```

**24 个真实版本，每个都有精确到秒的 bump 时刻。** 不需要 tag，不需要手写切点，不需要 git-cliff。

我昨天之所以判错，是因为**我只看了 `milestones` 这一份二手台账，没去看 `version.json` 的一手历史**。
`milestones` 里的 33 个版本有 11 个是**凭空造的**（`version.json` 从未有过）：

```
0.1.0 ~ 0.8.0  （Flask 本地版时期，历史遗留，合理）
1.1.0 / 1.2.0 / 1.14.0  ← PWA 时期手工虚构，这才是版本序列断裂的根源
```

**一句话：真正的版本真源一直在 git 里，我们却在手工维护一份会腐烂的副本。**

## 1. 实测：全自动切点能产出什么

我按「版本边界 = `version.json` 被改成该版本的提交时刻」重跑了全量分桶（脚本见 §7），结果：

| 版本 | 自动推导条数 | 当前实际条数 | 差异 |
|---|---|---|---|
| 1.16.0 | **6** | 0（不存在） | ← 凭空缺失的版本自动出现了 |
| 1.17.0 | **10** | **77** | **少 67 条** |
| 未发版 | **67** | 0（不存在） | ← 昨天诊断的「62 条挤进 1.17.0」就是这 67 条 |

**1.17.0 从 77 条降到 10 条，多出的 67 条变成一个语义正确的「未发版」桶。**

这不是修补，这是**结构上就不可能再出错**：
- 版本边界由 git 提交时刻决定 → **不可能漏加切点**（没有切点可加）
- 超过最新 bump 时刻的提交 → 自动进「未发版」桶 → **不可能挤进已发版卡片**
- 版本号序列由 `version.json` 历史决定 → **不可能跳号、不可能虚构**

昨天我提的 C-1（越界检测）、C-2（补 1.18.0 切点）、C-10（版本连续性校验）——
**三条全部消失，因为问题本身不存在了。**

## 2. 对抗性审查：这个方案自己的漏洞

我试着把自己这个方案打死。

### 漏洞 0（**原型实跑发现，最严重**）：手工切点与自动切点混用会产生空桶和错位

我第一版原型把「0.x 手工 + 1.x 自动」混在一起跑，结果**直接翻车**：

```
1.2.0    0 条  (空)      ← 手工切点 18:00 与自动切点 13:57 冲突
1.1.0    3 条            ← 顺序错乱，1.3.0 排到 1.1.0 前面
1.3.0   13 条
```

原因：`milestones` 里 `1.0.0 / 1.1.0 / 1.2.0` 的手工 `until`（06:00 / 12:00 / 18:00）与
`version.json` 的真实 bump 时刻（13:57）**互相打架**，排序后边界重叠。

**修正**：分界必须干净——**`0.x` 用手工切点，`1.x` 全部自动，中间不留缝**。
修正后 `1.2.0` 空桶消失，`1.3.0` 回到正确位置。

**这条是原型跑出来的，不是想出来的。说明"分层"必须验证，不能假设。**

### 漏洞 0.5：`1.16.1` 是天然空版本

修正后仍有一个空桶：`1.16.1`（0 条）。

查原因：`1.16.0` bump 在 22:01，`1.16.1` bump 在 22:11，**中间 10 分钟零提交**——
那次 patch 只改了 `STATE.md` / `changelog.json`，没有代码改动。

**这是真实情况，不是 bug。** 但渲染时会出现一张「v1.16.1 · 0 条」的空卡片。

**处理**：自动推导下，空版本**自动隐藏**（或合并进前一版，标注「仅构建号变更」）。
现有 `gen_changelog.py` 的 `self_check` 已经把「空版本」判为问题——这个逻辑要改成
「自动推导出的空版本不算问题，手工切点的空版本才算」。

### 漏洞 1：早期 0.x / 1.1.0 / 1.2.0 / 1.14.0 怎么办？

`version.json` 只有 24 个版本，`milestones` 有 33 个。纯自动推导会**丢掉 11 个版本**，
其中 `0.1.0~0.8.0` 是 Flask 本地版真实历史（有内容），不能丢。

**反击**：不是二选一，而是**分层**，但**分界必须干净**（见漏洞 0 的教训）：
- `0.x` 与 `1.1.0/1.2.0`：**保留手工切点**（历史已封存，不需要再维护，只读不改）
- `1.0.0` 之后：**全部自动推导**（version.json 有完整记录）

⚠️ 原型实测：混用会翻车。**最终分界定在 `1.0.0`**——`0.x` 手工，`1.0.0` 起全自动。
`1.1.0/1.2.0` 这两个虚构号随自动推导自然消失（它们的提交归入 1.0.0 或 1.3.0，见 §1 实测表）。

`1.14.0` 这个幽灵版本：它是 10-31 21:33 的推送功能，而 1.16.0 bump 在 22:01。
自动推导会把推送功能归进 **1.16.0**（正确！），1.14.0 卡片自然消失。
**这不是损失，这是修正** —— 因为 1.14.0 从来没上线过。

### 漏洞 2：版本号跳号（1.13.0 → 1.16.0）会保留下来

自动推导忠实反映 `version.json`，所以跳号会**继续显示**。

**反击**：这恰恰是**如实反映**。跳号是历史事实，伪造 `1.15.0` 只会制造更多假信息。
正确做法是**显示跳号 + 在发版脚本里禁止未来再跳**（`release.py` 已用 `bump_minor` 只 +1，
跳号只可能是手工 `--version` 造成，加个校验即可）。

### 漏洞 3：「未发版」桶显示给用户看，会不会很怪？

用户打开更新记录，看到「未发版 67 条」——他会问「那我到底更新了什么？」

**反击**（这条是真的需要设计）：**加上 `dev` scope 白名单后，这个桶大幅缩水**。实测：

```
未发版桶总条数：67 → 50（加 scope 白名单后）
  其中 dev（折叠）：37
  其中用户可见：13  ← 真正需要展示的只有这 13 条
```

13 条，且内容都是**真正的产品改动**（19 套整篇设计、字号调节、抽屉两 tab、贴图恢复……）。
这跟「67 条技术流水账」完全不是一回事。

**最终设计**：
- 「未发版」桶**默认折叠**，标题写「下次更新内容（13 项）」
- 只在 `#upd-demo` 和开发者视图里展开
- 用户主视图只看已发版版本卡
- 发版时这个桶自动变成新版本卡

**这个设计其实有价值**：它让「攒了三天没发版」这件事**变得可见**——你一眼就能看到「哦，攒了 13 项还没发」。现在的情况是这 13 项被埋在 1.17.0 的 77 条里，谁也不知道。

### 漏洞 4：`version.json` 的 bump 时刻 ≠ 上线时刻

10-31 21:10 bump 1.13.0，但部署是 21:05（b337）。**bump 早于部署**？说明版本号和部署顺序会错位。

**反击**：这是**流程问题**，不是生成器问题。而且 `build` 号可以精确反查部署点：

```
线上 b414 → git rev-list 第 414 个提交 → 338cf5e (2026-11-03 12:43)
```

**所以「已部署」这个语义有精确真源**（线上 `version.json` 的 build 号），不需要猜。

### 漏洞 5：这么改要动多少代码？

诚实核算：

| 改动 | 行数 |
|---|---|
| `gen_changelog.py` 加自动推导 + 未发版桶 | ~70 行（**替换** 现有 `ensure_milestone` 的 ~50 行） |
| 删 `milestones` 里 1.0.0 之后的 24 条手工记录 | -600 行 JSON |
| `changelog.js` 未发版桶渲染（折叠） | ~30 行 |
| 条数口径统一（C-4） | ~10 行 |
| `dev` scope 白名单（C-6） | ~10 行 |

**净变化约 +60 行代码 / -600 行配置。** 比昨天提的「补 5 个洞」少一半工作量。

## 3. 更彻底的解法：干脆不要自动生成条目

我继续往下推一层。用户真的需要看 172 条 commit 吗？

实测：**现有手写亮点 74 条 / 3575 字**，已经覆盖了 18 个版本。而全量自动条目是 370 条。

**方案对比**：

| 方案 | 用户看到什么 | 维护成本 | 乱的风险 |
|---|---|---|---|
| 现状（全量自动 + 折叠） | 每版最多 23 条，大量开发黑话 | 零 | **高**（77 vs 23 对不上） |
| 昨天建议（补 5 个洞） | 每版 3 条 + 展开 | 低 | 中 |
| **本方案（自动切点 + 未发版桶）** | 每版 10 条以内，语义正确 | **零** | **低** |
| 激进方案（只留手写亮点） | 每版 3 条人话，零 commit | 每版手写 3 条 | 最低，但**发版必须写文案** |

**我的判断：走第三方案，第四方案作为可选开关。**

理由：第三方案已经让「乱」的根因消失（切点零人工 + 未发版语义正确），且**不需要每次发版手写文案**。
第四方案虽然最干净，但把「每次发版必写 3 条人话」变成硬门槛——你昨天就是因为漏了手工动作才出事，
再引入一个人工动作，等于重蹈覆辙。

**折中**：第三方案打底，手写亮点**有则优先展示**（现有逻辑已支持 `milestone.highlights`）。
自动条目退化为「开发者细节」的补充，不占主视图。

**这是最讽刺的地方**：我们花 434 行代码 + 33 条手工 JSON 去重建一个 git 已经免费提供的事实。

## 6. 对抗性自检：这套改完，会不会有新问题？

| 风险 | 评估 | 缓解 |
|---|---|---|
| 自动推导依赖 `version.json` 的 git 历史，若有人手改历史（rebase） | 低（历史已推送到 GitHub） | 生成器加断言：真实版本数 >= 20 才继续 |
| 早期 0.x 手工切点与自动推导混用，边界重叠 | 中 | 明确分界点 `1.0.0`：之前手工，之后自动 |
| 未发版桶 67 条，发版后会变成一张 67 条的大卡 | **高** | 发版前必须写亮点；或未发版桶按天再分块 |
| 面板 UI 要改渲染逻辑 | 低 | 已有 `<details>` 折叠机制可复用 |
| 回归测试 `pwa_update_panel_test.py` 断言「本次更新 N 条」 | 中 | N 会从 77 变 10，断言仍成立（N>0） |

**唯一需要你决策的是第 3 条**：67 条的未发版桶，发版时要不要强制写亮点？
- **A**：强制（`release.py` 检查 highlights 非空，否则拒发）→ 干净，但多一道人工动作
- **B**：不强制（自动从可见条目挑 3 条兜底，现有 `auto_highlights` 逻辑）→ 零人工，但可能不好看

我倾向 **B**，理由见 §3 末：你昨天出事就是因为多一道人工动作。

## 7. 复现脚本（证明自动推导可行）

```bash

git log --format="%H %ci" -- pwa/version.json | while read h d t rest; do
  v=$(git show $h:pwa/version.json | python -c "import json,sys;print(json.load(sys.stdin)['version'])")

done
```

## 7.1 原型验证暴露的两个坑（写进方案前必须知道）

| 坑 | 现象 | 结论 |
|---|---|---|
| 手工 + 自动混用 | `1.2.0` 空桶、`1.1.0/1.3.0` 顺序错乱 | **分界必须干净：`0.x` 手工，`1.0.0` 起全自动** |
| 天然空版本 | `1.16.1` 0 条（bump 间隔 10 分钟无提交） | 自动推导的空版本**自动隐藏**；手工切点的空版本仍报错 |

### 原型最终验收（实跑数字）

```
用户可见版本数：31（总边界 32，隐藏空版本 1 个 = 1.16.1）
最近 6 个可见版本：1.10.0(5) 1.11.0(5) 1.12.0(12) 1.13.0(5) 1.16.0(6) 1.17.0(10)
现状：33 个版本，1.17.0 有 77 条
```

**关键变化**：
- 1.17.0：**77 条 → 10 条**
- 1.16.0：**不存在 → 6 条**（自动补回）
- 1.14.0：**3 条 → 消失**（幽灵版本，从未上线）
- 未发版 67 条：**从 1.17.0 里移出**，进独立桶
- 总数 370 条**一条不丢**
