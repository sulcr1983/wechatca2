# 自动配图调研 · 成熟做法与适合本项目的技术方案

> 调研日期：2026-11-02
> 状态：**方案稿，未接线**。本文只回答「该怎么做」，不含任何代码改动。
> 相关代码：`pwa/src/editor-images.js`（粘贴/上传 → 压缩 → data URI）、`pwa/src/images.js`（外链图本地化）、
> `pwa/src/cover/search.js`（Pexels BYOK 搜图）、`pwa/src/ai.js`（`suggestImageKeywords()` / `analyzeContent()`）。
> 项目铁律：**纯文本进排版出；不用 AI 就不开 AI；每个降级说明原因、不静默。**

---

## 0. 一句话结论

**做 L1（自动定位建议位），把 L2（自动搜图）做成一次点击，坚决不做 L3（全自动插入）。**

理由不是保守，而是三条硬约束：

1. 本项目**默认零 AI、纯前端离线可用**。L3 需要"判断哪里该配图 + 配上什么图"，判断力和图库都在云上，
   等于把默认路径改成「必须联网 + 必须配 Key」，与产品定位直接冲突。
2. 唯一的图源 Pexels 是 BYOK（`pwa/src/cover/search.js` 已收敛为单源）。**没 Key 的 L3 等于静默失败**，
   而铁律要求「每个降级说明原因」。一个「不配 Key 就永远不配图」的自动功能，不如不做。
3. 现有代码已经证明「人工确认后插入」这条路是通的（`insertMarkdownImage` 的独占段落规则、
   data URI 内嵌实测可粘进公众号）。自动化的价值集中在**省掉"想在哪插图"这一步**，
   而不是省掉"看一眼图对不对"这一步 —— 后者一旦交给机器，产物就是「图文不符」。

> 来自**官网首页与产品页文案**，我**没有登录实际点过**，所以"自动化级别"一列对这两家是**推定**。

### 1.1 从对比里读出的三件事

- **开源阵营普遍不做自动配图**（doocs/md 干脆没有，md2wechat 只做"生成封面/信息图"和"给建议"）。
  做全自动的是**商业 SaaS + 版权素材库**的闭环玩家（135）。他们敢自动插图，是因为图来自自己的
  已授权素材库、且用户在自家云端编辑器里，误插可以直接撤销云端草稿。
- **"建议位置"和"自动插入"是两种产品**：md2wechat 的 `advise` 特意写明「不编辑文章」。
  这是把"判断"和"落笔"分开 —— 值得直接抄。
- **配图能力的强弱取决于图源授权，不取决于算法**。我们只有 Pexels（免费商用、无需署名、原生支持中文），
  够用但覆盖窄，所以更不能自动插。

## 2. L1 / L2 / L3 的取舍

定义：
- **L1 自动定位**：规则算出「建议在第几段后插图 + 该位置的关键词 + 为什么选这里」，不联网、不改文。
- **L2 自动搜图**：在 L1 给出的位置和一键操作下，调图库搜出候选图，用户点选。
- **L3 全自动插入**：机器自己决定位置、自己选图、自己写进正文，用户事后才发现。

| 维度 | L1 自动定位 | L2 一键搜图 | L3 全自动插入 |
|---|---|---|---|
| 需要联网 | 否 | 是（Pexels） | 是 |
| 需要 Key | 否 | 是（BYOK，用户自己的免费 Key） | 是 |
| 需要 AI | 否（规则） | 否（关键词也可纯规则） | 通常要（判断语义） |
| 默认路径是否被改变 | 否（只是多一块提示） | 否（要点一下） | **是**（粘贴完就已经有图了） |
| 违反铁律的风险 | 低 | 中（必须处理"没 Key/搜不到"的说明） | **高**（位置错、图错、静默失败全犯） |
| 用户心智负担 | 降低（把"想在哪插图"变成"确认/换一个"） | 降低（省掉手打关键词） | 归零，但换来"得逐张检查" |
| 实现成本 | 低（纯规则，几十行） | 中（接线已有 search.js + 选图 UI） | 高（还要撤销、还要配额、还要解释为什么） |
| **本项目结论** | ✅ **做** | ✅ **做，但必须是一次点击** | ❌ **不做**（除非将来有明确的「我知道风险」开关） |

### 2.1 L1 为什么用规则而不是 AI

依据本项目已有判断（`pwa/src/ai.js` 的注释里已经引过同一组论文）：

- **版面/空间决策不该交给 LLM**：LaySPA（arXiv:2509.16891）指出 LLM 的空间/版面推理很弱，
  内容感知版面要素需要额外增强。而"图该放在哪一段后面"**正是**版面决策。
- **选对结构类型是关键、且规则比通用大模型零样本更准**：StructRAG（ICLR 2025）的实测是
  专用路由 94% vs 通用模型零样本 50%。本项目 `analyzeContent()` 已经是这个思路（数据型/清单型/
  方法型/叙事型四类 + 装饰预算）。
- **AI 在这里的增量很小**：位置判断主要看「段落长度、是否小节边界、是否已有图、是否列表/表格、
  图片配额还剩几张」—— 全是可测量的确定性信号，没有一处需要语义理解。

AI 唯一真正独占的是「**这段话讲的是什么主题**」→ 该用什么图。而这恰好只影响 **L2 的搜索关键词**，
不影响 L1 的位置。所以：
> **位置用规则（永远可用）；关键词优先用规则（本地词频），用户配了 AI 才可选 AI 精修。**

这条分工把「不用 AI 就不开 AI」落到了具体的一行代码边界上。

### 2.2 L3 为什么明确不做

四条理由，任何一条单独都足够：

1. **图库覆盖不够**。单源 Pexels，中文查询靠它原生支持；美食/旅行/职场/生活方式覆盖好，
   政策解读、产品发布、技术教程几乎搜不到合适图。L3 遇到搜不到只能①硬塞（图文不符）
   或②跳过（静默）—— 两条都踩铁律。
2. **位置错一次的成本高于省下的时间**。段落之间插错图，用户得先找到它、再删掉、再重新插。
   省 3 秒、赔 15 秒。
3. **无法撤销干净**。我们的产物是 Markdown 源码（`![](...)` 独占一段）+ 实时预览。
   自动插入要额外维护"哪些图是机器加的、撤销时删哪几段"，这是纯负债。
4. **data URI 的体积账**。`editor-images.js` 定的是 150KB/张、单次上限 8MB。
   自动插 5 张就是 750KB 塞进剪贴板。图是机器选的，用户没参与，却要承担粘贴变慢 —— 体验倒退。

## 3. 推荐方案：L1 规则定位 + L2 一键搜图

### 3.1 数据流

```
纯文本（用户粘贴）
   │
   ├─ analyzeContent(text)            ← 已有：内容类型 + 规模 + 装饰预算
   │
   ├─ locateImageSlots(text)          ← 新增（纯规则，本文 §4）
   │     ↓  [{para, score, keywordHint, reason, degraded?}]
   │
   ├─ UI：「建议配图位」卡片列表（可忽略、可换位、可整段关闭）
   │     ↓ 用户点「找图」
   ├─ extractKeywords(paraText)       ← 新增（本地词频，本文 §5）
   │     ↓ 中文关键词（Pexels 原生支持中文，不必强行翻英文）
   ├─ searchBackground(q)             ← 已有：Pexels BYOK 搜图 + 24h 缓存
   │     ↓ 候选 12 张（竖图）
   └─ insertMarkdownImage(textarea, dataUri)  ← 已有：独占一段、保证前后空行
```

关键点：
- **零新增网络请求**，除了用户主动点的搜图。落地即离线可用（只有 L1 部分）。
- **零新增 AI 依赖**。AI 精修关键词是可选旁路：`isVerified()` 为真才显示「用 AI 再提炼一次」。
- **复用既有三件套**（`searchBackground` / `fetchImageDataUrl` / `insertMarkdownImage`），
  不新写压缩、不新写缓存、不新写插入规则。

### 3.2 与现有代码的接线位置

| 复用 | 位置 | 说明 |
|---|---|---|
| 搜图 | `pwa/src/cover/search.js` → `searchBackground()` | 已有：Pexels BYOK、24h localStorage 缓存、按图源签名隔离、翻页、`needKey` 标记 |
| 关键词猜词 | 同文件 `guessQuery()` / `autoKeyword()` | 已有 ZH_EN 词表映射 + 中文直搜兜底 |
| 图转 data URI | 同文件 `fetchImageDataUrl()` | 已有：避免截图跨域污染 |
| 压缩 | `pwa/src/editor-images.js` → `fileToDataUri()` | 已有：1080 宽 / 150KB / 质量阶梯 |
| 插入 | 同文件 `insertMarkdownImage()` | 已有：独占一段，前后保证空行（否则 python-markdown 不认） |
| 内容画像 | `pwa/src/ai.js` → `analyzeContent()` | 已有：四类内容 + 规模系数 + 装饰预算 |
| AI 精修关键词 | 同文件 `suggestImageKeywords()` | 已有，门控在 `isVerified()` 之后 |

### 3.3 必须遵守的降级契约

铁律「每个降级说明原因、不静默」在这里的落地方式：**每个建议位都带一个机器可读的 reason code**，
UI 直接展示人话。参考 `images.js` 的既有做法（每张失败的图都带可读原因）。

| code | 人话文案 | 触发条件 |
|---|---|---|
| `ok` | 建议在此配图 | 通过全部规则 |
| `no_key` | 还没配置 Pexels Key，只能看建议位置、搜不了图。点「填 Key（免费·2分钟）」 | `availableProviders()` 为空 |
| `no_hit` | 这个词在 Pexels 没找到合适的图，换个关键词，或在此留白 | 搜索返回 0 条 |
| `kw_weak` | 没能从这段文字里提取到具体、可拍的关键词（只有抽象概念），建议你自己填 | 本地关键词全是停用词/抽象词 |
| `kw_abstract` | 「成功/未来/效率」这类抽象词搜不到好图，已跳过 | 命中抽象词黑名单 |
| `too_dense` | 这一段离上一张图太近，插了会显得碎 | 间隔 < 阈值 |
| `already_has_img` | 这一段已经配过图了 | 段落内含 `![](` 或 `<img` |
| `quota_full` | 全文建议配额已用完（本文较长，再加图会打断阅读） | 达到上限 |
| `ai_failed` | AI 提炼失败（原因：…），已退回本地关键词 | AI 抛错 |
| `offline` | 当前离线，只能给出建议位置 | `!navigator.onLine` |

**禁止行为**：搜不到就换一个不那么相关的词再试；搜不到就悄悄跳过不给提示；用户没点就发请求。

## 4. 确定性规则清单（可机检）

以下规则全部只用「段落文本 + 段落序号 + 全文统计」，不需要语义理解，可写成纯函数并单测。
每条都给出**可判定的阈值**，不给"适当"这种词。

### R0 前置：把文章切干净

```
paras = text.split(/\n\s*\n/).map(trim).filter(Boolean)
```
- 判重前提：与 `ai.js` 的 `planStructure()` 用**同一个切段方式**（同样 `\n\s*\n`），
  否则段落号对不上，AI 结构决策和配图建议会指向不同段落。
- 特殊段落打标：`isHeading`（`#` 开头 / `preprocessor` 判为小标题）、`isList`（`·•●` 或 `-* ` 开头）、
  `isTable`（含 `|` 且下一行是 `---|---`）、`isFence`（`:::` 围栏容器 / 代码块）、
  `isQuote`（`>` 开头）、`isCallout`（`:::` + `callout|note|tip|warning`）、`hasImg`（`![](` / `<img`）。

### R1 段落资格（谁能成为候选位）

一条段落要成为候选，必须**同时**满足：

| 规则 | 判据 | 为什么 |
|---|---|---|
| R1.1 不已有图 | `!hasImg` | 避免叠图 |
| R1.2 不是结构件 | `!isHeading && !isList && !isTable && !isFence && !isQuote && !isCallout` | 列表/表格/围栏里插图会破坏结构；标题后紧跟图属"lead image"，单独走 R3 |
| R1.3 段够长 | 去空白后 `len >= 60`（中文按字符计） | 太短的段落没有信息量，配图变装饰 |
| R1.4 不是纯数字/符号 | 中文字符占比 `>= 30%` | 避免把代码段、公式段、编号段当正文 |
| R1.5 不是首段/末段 | `i > 0 && i < paras.length - 1` | 首段是标题区，末段是结论；结论段配图打断收尾 |

### R2 位置打分（同一篇文章里谁优先）

`score = 0` 起步，逐条累加（权重是我给的初值，**上线后应按真实样本调**）：

| 信号 | 分值 | 判据 |
|---|---|---|
| 紧跟小节标题 | **+3** | 前一段 `isHeading` 为真（新话题开场最适合配图） |
| 话题转折词开头 | **+2** | 段首 12 字内命中 `但是|不过|于是|结果|后来|反而|与此相反|另一方面|换个角度` |
| 段首是完整陈述句 | **+1** | 段首 40 字内含 `。`（说明这段在讲一件事，不是续句） |
| 段落偏长 | **+1** | `len >= 200`（视觉上需要断开） |
| 段落极长 | 额外 **+1** | `len >= 400` |
| 与上一张候选图距离 | 距离 `>= 3` 段 **+1**；距离 `< 2` 段 **-5**（近似否决） |
| 命中具体意象词 | **+2** | 见 §5 的词表/词频结果非空且命中具体名词 |
| 命中抽象词 | **-3** | 见 §5 抽象词黑名单 |

### R3 三张"固定位"（不受 R1.5 / R2 约束，单独判断）

1. **Lead image（标题后第一张）**：如果 `paras[0]` 是标题（`preprocessor` 判为标题，或首段 `len <= 30`
   且无句号），建议在 `paras[1]` 之前配一张。**上限恒为 1**。这是行业最稳的一条
   （Wikipedia MoS/Images 把它单列成 "Images for the lead"，公众号「封面图」也是同一个心智）。
2. **小节级配图**：每个 `isHeading` 后第一段，若通过 R1.1~R1.4，则是一个强候选（等价 R2 的 +3）。
3. **结尾不配图**：`paras[last]` 之后永不建议。理由：公众号结尾通常是金句/引导关注，
   插图会把注意力从结尾文字上拽走。

### R4 图片配额（防"满屏都是图"）

按 `analyzeContent()` 已有的规模分档取上限，与装饰预算同源（保持"预算由规则算好"的一致性）：

| 正文字数 | 建议配图上限 | 备注 |
|---|---|---|
| `< 300` | 1 | 短文只要 1 张（通常就是 lead image） |
| `300 ~ 799` | 2 | |
| `800 ~ 1999` | 3 | |
| `>= 2000` | 4 | 触顶后所有后续候选标 `quota_full` |
| 任意长度 | **硬上限 6** | 超过 6 张后，`data URI` 剪贴板体积压不住（见 §2.2 第 4 条） |

并且：**任意两张建议位之间至少隔 2 个候选段落**（R2 里的 -5 就是这条的软实现；
配额阶段再做一次硬过滤）。

### R5 内容类型对配图的抑制（与 `CONTENT_RULES` 对齐）

| 内容类型 | 配图策略 | 依据 |
|---|---|---|
| `dataly`（数据型） | 上限 **-1**，且优先提示「这段更适合做成表格/数据卡」而非配图 | 数字是主角，插图会分散；项目已有表格能力 |
| `listy`（清单型） | 上限 **-1**，只在 lead image 和第一个小节配 | 清单本身已有节奏，插图破坏它 |
| `tech`（方法型） | 正常；但 `:::steps` / 代码块附近 2 段内不配 | 步骤连续阅读不能被图打断 |
| `narrative`（叙事型） | 正常，可略高（+1），偏好话题转折处 | 叙事文靠图断句是常见排版手法 |

### R6 全篇否决条件

命中任一条 → **不出任何配图建议**，并说明原因（一条 `degraded` 记录）：

- 正文去空白后 `< 150` 字 → `too_short`：「文章太短，不需要配图」
- `paras.length <= 2` → `too_short`
- 已有图数量 `>=` R4 上限 → `quota_full`：「正文里已经有 N 张图了」

### R7 可机检性说明（怎么测）

全部规则是 `(text: string) => Slot[]` 的纯函数，无 DOM、无网络、无异步，可直接被门禁单测覆盖。
建议夹具（沿用项目既有夹具思路：短 / 标准 / 复杂三类）：

| 夹具 | 期望 |
|---|---|
| 100 字无标题短文 | 0~1 个建议位，且必须是 lead image |
| 800 字 3 小节叙事文 | 2~3 个建议位，位置都在小节开头附近 |
| 1500 字含 2 个表格 + 1 个列表的清单文 | 建议位不落在列表/表格上；上限 -1 |
| 已有 3 张 `![](...)` 的正文 | 这些段落不出现建议位；上限相应递减 |
| 纯代码 / 纯英文 / 纯数字正文 | R1.4 全部否决 → 0 个建议位 |
| 同一篇连跑两次 | 输出完全一致（确定性，无随机、无时间依赖） |

**确定性要求**：同一输入必须给同一输出。任何用到 `Date.now()` / `Math.random()` /
网络结果的分支都不许进 L1。

### 5.2 推荐组合

```
Intl.Segmenter(zh, {granularity:'word'})        ← 分词，0 体积
  + 停用词表（stopwords-zh 的 10KB，或自建 200 词）  ← 去噪
  + 抽象词黑名单（成功/未来/效率/价值/认知...）       ← 只留「可拍」的词
  + 现有 ZH_EN 词表（search.js 已有 47 条）          ← 中文 → 英文精修（Pexels 可选）
  + 词频（段落内）+ TF-IDF（全篇为语料）             ← 排序
  → top 3 词，中文串直接丢给 Pexels（原生支持中文）
```

**为什么用 TF-IDF 而不是纯词频**：纯词频会把「我们」「这是一」这种全篇高频词顶上来（停用词能挡一部分，
但挡不干净）；TF-IDF 用**同一篇文章的其他段落**当语料，"这段独有的词"自然浮上来 —— 这正好是
"这段在讲什么"的近似。实现是 20 行数学，不需要库：

```
tf(t, d)  = 该词在本段出现次数 / 本段总词数
idf(t, D) = log(段落总数 / 含该词的段落数) + 1      ← +1 防 log(1)=0 把单段独有词打成 0
score     = tf * idf，取 top K
```

**20 行内的实现要点**（写进方案供后继实现）：
- 先按 `Intl.Segmenter` 切词，`isWordLike` 为假直接丢；
- 长度过滤：单字全丢（中文单字几乎无检索价值），`len >= 2` 保留；
- 停用词 + 抽象词黑名单过滤；
- 同段去重后按 TF-IDF 排序取前 3；
- 与 `ZH_EN` 表做最长匹配（沿用 `guessQuery()` 的"按长度优先"逻辑），命中则附带英文词。

### 5.3 性能与体积预算

| 项 | 预算 | 说明 |
|---|---|---|
| 新增代码体积 | **< 9 KB**（gzip 后 < 4 KB） | 纯手写规则 + 词表，不引第三方分词库 |
| 词表体积 | **< 12 KB** | 停用词 + 抽象词黑名单 + ZH_EN（已有） |
| 运行耗时 | **< 50 ms**（3 万字） | `Intl.Segmenter` 是原生实现；TF-IDF 是两趟哈希表遍历 |
| 首次落地额外网络请求 | **0** | 与 Pexels/搜图完全解耦 |
| 失败面 | 无网络可失败 | 唯一可能失败点是 `Intl.Segmenter` 不存在 → 降级为"按标点切分 + 2-4 字滑窗取高频"，并标 `no_segmenter` 说明原因 |

**降级链（必须写出来，不许静默）**：
```
Intl.Segmenter 可用 → 分词 + 去停用词 + TF-IDF
  ↓ 不可用（老浏览器）
标点切分 + 2~4 字滑窗 n-gram + 词频，标 reason=no_segmenter
  ↓ n-gram 也提不出具体词
不出关键词，该建议位标 reason=kw_weak，让用户自己填
```

## 6. 落地顺序（供后继实现参考，本文不改代码）

1. **P1 · 纯规则定位**（零网络、零 AI）：`locateImageSlots()` + 单测夹具（§4.7）。
   此时功能表现是「正文下方一块『建议配图位 3 处』列表，点某条跳到该段」，不搜图。
2. **P2 · 本地关键词 + 接线搜图**：`extractKeywords()` + 复用 `searchBackground()`，
   用户点「找图」才发请求；`no_key` / `no_hit` 全部走 §3.3 的文案。
3. **P3 · 可选 AI 精修**：`isVerified()` 为真时多一个「用 AI 再提炼」按钮，
   调已有的 `suggestImageKeywords()`，失败退回本地词并标 `ai_failed`。
4. **不做**：L3 全自动插入、后台静默预搜、按 `Date.now()` 抖动的"热门图"。
