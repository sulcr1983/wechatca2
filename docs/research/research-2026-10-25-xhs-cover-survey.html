小红书封面生成方案调研
与 SuperSu 借鉴建议

对 GitHub / npm 上主流的小红书封面与图文卡片生成方案做横向拆解，提取实现思路、布局排版、字体与配色处理的可借鉴做法，并核对许可边界。

调研日期 2026-10-25 项目 SuperSu（wechatca2） 范围 7 个方案 + 5 个渲染组件 结论 借鉴思路可行，代码需按许可分档

00先说结论

整体判断：我们缺的不是模板数量，是「多页 + 结构化」能力

项目已有 12 套封面风格（2 套归藏内置 + 10 套归藏模板）、modern-screenshot 渲染管线、fitty 字号自适应、得意黑可选字体。跟外部方案比，视觉资产不缺，缺的是三件事：① 多页/轮播（分页算法）；② 风格 × 版式的正交组合（现在是 12 套扁平主题，N 套风格要写 N 个模板）；③ 排版质量的可验证性（现在靠肉眼，外部已有 DOM 测量校验）。

最大的风险不在「要不要抄」，而在 BLCaptain 的自定义双许可

归藏（AGPL-3.0）我们已经在用，且项目整体也以 AGPL-3.0 发布、THIRD_PARTY_NOTICES.md 已履行 §5/§13 义务 —— 这部分是合规的。但 BLCaptain 是自定义双许可，其声明写明「改为闭源部署或商用须先取得书面商业授权」。SUPERSu 目前线上是 supersu.ccwu.cc，属于自用性质尚可；一旦要商业化，这是必须提前处理的硬约束。

许可分档（决定「能抄到什么程度」）

可直接借鉴代码（保留版权声明即可）：Auto-Redbook-Skills (MIT)、baoyu-skills (MIT)、XHS_Cover (MIT)、xhs-toolkit (MIT)、modern-screenshot / snapdom (MIT)。

只能学思路、不能抄代码/模板：归藏 (AGPL-3.0) —— 与我们的 AGPL 主许可兼容，但若将来要闭源商业版，其版式与 CSS 必须彻底重写。

需商业授权：BLCaptain Style Skill（自定义双许可）。

组件库可链接使用、改动源文件才需开源：satori (MPL-2.0)，文件级 copyleft，不传染调用方。

一个容易被忽略的信号：小红书上出现的大量项目其实是「Skill + 渲染脚本」形态，不是传统 Web 应用。它们的共同取舍是 AI 只负责产文案与选版式，绝对不让 AI 负责画字 —— 因为文生图模型的文字准确率不可控。这条正好和我们「纯文本进、排版出、不开 AI 也能用」的定位一致，是方向上的正面验证。

02关键方案拆解

Auto-Redbook-Skills

MIT · 可借鉴代码
github.com/comeonzhj/Auto-Redbook-Skills
渲染
Markdown → marked 解析 → HTML 模板 → Playwright 截图。Python 与 Node 各一套实现，参数对齐。
主题
每个主题一个独立 CSS 文件挂在 assets/themes/，共用 styles.css 定义容器骨架。主题只改「排版 + 内层背景」，不动外层结构。
分页
四模式：separator（按 --- 手动）/ auto-fit（固定尺寸整体缩放）/ auto-split（按渲染高度自动拆）/ dynamic（高度随内容）

可直接借鉴的三处

  • 三层卡片结构：.card-container（1080 宽、浅灰渐变底、padding 50）→ .card-inner（白底 95% 透明、圆角 20、padding 60、min-height: calc(1440px - 100px)、轻阴影）→ .card-content（纯排版 42px/1.7）。结构层与主题层彻底解耦，换版式不用重写内容样式。
  • 精确尺寸基准：封面容器 1080×1440，内层 950×1310 偏移 (65,65)，padding 60px 85px。这类「外层留白 65 / 内层 padding 85」的双重边距是杂志感的关键，比单层 padding 稳。
  • 字号阶梯：封面标题 130px / weight 900 / line-height 1.35（渐变文字）、副标题 72px / weight 350；正文卡 h1 72 / h2 56 / h3 48 / 正文 42，全部 line-height 1.3~1.7 递增。

中文断行处理（细节但关键）

标题用 word-break: normal; overflow-wrap: break-word —— 让浏览器按中文词法断行，只在超长无空格串时强制断。代码块用 white-space: pre-wrap + overflow-wrap: break-word 替代横向滚动（截图场景滚动条会被截进去）。这两条我们 textmode.js 里应按字逐一 span 时特别注意，逐字包裹会破坏浏览器原生断行。

归藏 social-card skill

AGPL-3.0 · 仅学思路
github.com/op7418/guizang-social-card-skill
渲染
单文件 HTML（内嵌全部 CSS）+ Playwright render.mjs → PNG。刻意不做前端构建链，理由是「HTML/CSS 是文本，Agent 能直接读写改验证」。
体系
两套视觉系统共用一套工作流：Editorial（杂志风，氛围叙事）+ Swiss（瑞士风，事实结构）。3 个画板尺寸：.poster.xhs 1080×1440 / .poster.wide 2100×900 / .poster.square 1080×1080。
主题
10 套预设，切换只改 <section class="poster" data-theme="..."> 一个属性，CSS 全走 var(--...)。

最值得学的是「约束」而不是「素材」

  • 不允许自定义 hex 值 —— README 原话是「保护美学比给自由更重要」。这条我们已经在 catalog.js 的 swatch/accent 里做到了雏形，但没有显式禁止用户改色。
  • validate-social-deck.mjs：用 Playwright 跑真实 DOM 测量，自动检测溢出、字号上限、四横带密度、footer 碰撞。这是「排版质量可验证」的样板 —— 我们完全可以照此思路写自己的检查脚本（思路借鉴，非代码）。
  • 文字压图的 quiet-zone 与主体避让：满铺图先算出「可安静放字的区域」与「人脸/产品/关键动作」的映射，文字避开主体；只在需要时加局部 tint，不默认整图遮罩。
  • 字号 / 字距 / 字重有对照表：references/components.md 逐组件列出三值，改模板要同步更新表。这正好命中我们「文档必须与代码同步」的痛点。

红线：AGPL-3.0 下，其 CSS 变量体系、版式骨架、校验脚本的具体实现不能搬进任何非 AGPL 的姊妹项目。当前 SuperSu 整体 AGPL + 已提供源码，内部使用与修改是合规的；但「读它的代码然后换个写法搬过来」在闭源场景下同样有风险。安全做法：只取设计原则（如「禁止自定义色值」「校验四横带密度」），实现自己写。

baoyu-skills · baoyu-xhs-images

MIT · 可借鉴代码
github.com/JimLiu/baoyu-skills

整个仓库 20+ skill，与本项目相关的是 baoyu-xhs-images（1-10 张图文卡片）与 baoyu-cover-image（五维度 × 77 组合）。

核心借鉴：正交维度而非扁平清单

它把「长什么样」拆成三个互相独立的轴：

  • Style（12）：cute / fresh / warm / bold / minimal / retro / pop / notion / chalkboard / study-notes / screen-print / sketch-notes
  • Layout（6）：sparse（封面/金句）/ balanced（常规）/ dense（知识卡）/ list（清单）/ comparison（对比）/ flow（流程）
  • Palette（3 可选覆盖）：macaron / warm / neon

12 × 6 = 72 种组合，但只需要维护 12 份风格 + 6 份布局。这正是我们 12 套扁平模板的解法：现在加一套风格要复制一整个 index.html，正交化之后加风格只写一份风格 CSS。

其 baoyu-diagram 还有一条值得记的产品判断：矢量图表类不调图片模型，让模型手写真实 SVG 代码。理由同样是文字准确性与可编辑性。

XHS_Cover / xhs-toolkit

MIT · 可借鉴代码
github.com/Smartloe/XHS_Cover · github.com/fifizy/xhs-toolkit

XHS_Cover：如果要做「可视化微调」，这是参考架构

React + Vite + Tailwind + Radix UI，核心交互库是 react-draggable（拖拽）+ react-color（取色）+ html-to-image（导出）。360×480 预览画布，导出 1080×1440（3 倍缩放）。

  • 文本分层：标题 / 高亮关键词 / 正文 / 标签，各层独立编辑 —— 比「一个 title 输入框」表达力强得多
  • 100+ Emoji 贴纸可拖拽 / 缩放 / 旋转，Delete 删除
  • 坑点记录：跨域图片导出需设 crossOrigin + referrerPolicy，否则导出空白。我们 images.js 做外链图本地化时同理

xhs-toolkit：最小可用的换肤范式

一个 --accent CSS 变量切换全篇主色（紫 #7C3AED 科技 / 橙 #FF6B00 热点 / 红 #E74C3C 争议 / 蓝 #2563EB 教程），背景固定暖白 #FDF8F3 + 白色卡片 + 彩色左边框 + 轻阴影。把「主题」压缩到单个变量，是我们低成本扩充风格的最快路径。

03横向提炼：排版 · 字体 · 配色

3.1 布局排版：外部共识的四条硬规则

规则具体做法出处
上重下轻 信息流里封面底部约 15%（约 120px）会被标题+作者头像遮罩覆盖。上部 2/3 放核心信息（大标题、数字、主视觉），下部 1/3 只放装饰。内页不受此限。 huashu-skills 设计规范 / spellbook-xiaohongshu
字号锚点公式 主标题 ≈ 画布宽 ÷ 7 ~ ÷ 6。1080 宽 → 154~180px 较稳。三级以下不低于宽度的 1/30（即 36px 以下在缩略图里不可读）。一级:二级 ≤ 3 倍差，否则缩略图糊成一团。 多篇设计规范交叉一致
缩略图自检 标题必须在 iPhone 信息流缩略图（约 170×227）下仍可读。做图时缩到 16% 看一眼，是我们现在完全没有的环节。 huashu-skills / Auto-Redbook issue
安全区 上下各 80px、左右各 60px；底部 120px 不放重要信息。 huashu-skills 设计规范

字号层级参考（1080×1440 画布）

层级规范建议Auto-Redbook 实测我们的处置建议
主标题80-120px（占比 30-50%）130px / 900落在 120-150px，按标题字数动态收缩
副标题40-60px（10-20%）72px / 35060-72px / 300-400（细体是杂志感来源）

3.2 字体处理：三条可执行的做法

  • 只用可商用字体，并明确写进代码注释。多份规范一致推荐：阿里巴巴普惠体 Bold（标题）、思源黑体 Bold/Regular、站酷庆科黄油体、站酷快乐体。明确避雷：方正、汉仪、华文系列（商用需授权）。有博主因未授权字体被索赔 2 万元的案例被反复引用。
  • 字体子集化 / 按需注入。中文字体动辄 5-10MB，直接内嵌会让 PWA 首屏不可接受。Auto-Redbook 用系统栈兜底（'Source Han Sans CN', 'PingFang SC', 'Microsoft YaHei', -apple-system），归藏则把字体路径改为本地。我们的 textmode.js 已经做了得意黑按需注入 + document.fonts.ready 等待，这条路是对的，可再补一层「只取用到的字形」。可考虑 fonttools pyftsubset 或 cn-font-split 做构建期子集。
  • 等字体就绪再截图。我们 render.js 里已经 await fonts.ready + 两帧 requestAnimationFrame 等 fitty 写回 —— 这是外部方案普遍踩过的坑，我们已经解决了。

3.3 配色处理：三条范式

范式做法代表适配我们的场景
主题预设锁色 预设 N 套完整色板（底/主/强调三色），禁止用户改 hex。切主题 = 改 data-theme 属性。 归藏（10 套）
Auto-Redbook（8 套）		 ✅ 我们现状。catalog.js 的 swatch/accent 已是雏形，可补「底/主/强调」三值
单变量换肤 背景与中性色固定，只让 --accent 变化。 xhs-toolkit（4 色） ✅ 低成本扩风格首选，一套骨架 × N 个 accent
调色板叠加 风格与配色正交，调色板作为可选覆盖层。 baoyu-skills（3 调色板） ⚠️ 需要先做正交化重构才有意义

配色的一条通用原则（多源一致）：深浅二选一不混用 —— 要么深底亮字，要么浅底深字；固定账号色板（2-3 套）形成品牌认知；避免低饱和灰底 + 浅灰字（信息流里直接淹没）。

06落地建议（按性价比排序）

P0

抽出「设计令牌」常量表 + 安全区约束

把散落在 12 个模板里的字号、边距、色值收敛成一组常量，一次性解决「数值口径不一」和「改一处要改十二处」。同时显式声明安全区：上下 80 / 左右 60 / 底部 120 禁区。

借鉴来源：huashu-skills 设计规范（行业数据）+ Auto-Redbook 的尺寸基准（MIT，可直接取值）。

pwa/src/cover/catalog.js 旁新增 tokens.js；各模板改为读令牌
P0

加一个「缩略图自检」开关

预览区一键把封面缩到 170×227（小红书信息流真实尺寸），让人眼直接判断标题是否还认得出。这个功能不到 30 行代码，但对成品率影响最大 —— 外部多份规范把它列为核心法则，我们现在完全没有。

借鉴来源：huashu-skills「缩略图测试」法则（思路，非代码）。

pwa/src/cover/index.js 预览区加缩放切换

07明确不做什么（避免抄袭与产品走偏）

  • 不搬归藏的 CSS 变量体系与版式骨架到非 AGPL 产物。它的设计原则（禁自定义色值、校验密度、主体避让）可以学，具体声明与几何数值自己重算。
  • 不做拖拽式画布编辑器。XHS_Cover 那条路（react-draggable + 贴纸）与「纯文本进、排版出」的定位相互冲突，会让我们退化成又一个 Canva。真需要微调，优先做「文案级参数」而非「像素级拖拽」。
  • 不引入 LLM 出图做封面主视觉。外部方案一致避开这条路，原因是文字准确率不可控。我们已有 image_search.py 找真图 + PIL 叠加，方向更稳。
  • 不接第三方付费封面 API（xhscover 那类）。核心能力外置会把产品命运交给别人。
  • 不追求模板数量。归藏 README 的判断值得记住：「2025 年起千篇一律的模板互动率持续下降」。我们的优势应是「同一套内容换气质」，而不是「164 个模板任选」。

调研方式：Web 检索 GitHub 仓库 README / 源码、npm 包文档、第三方设计规范文档；许可信息以各仓库 LICENSE 声明与 README License 段落为准。标注「未核实」者为仅见二手介绍、未见 LICENSE 原文，落地前需自行核对。
