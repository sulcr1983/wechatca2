## 2. 开源调查的关键发现（决定了本方案的形状）

完整调查见 [`research/research-2026-11-01-theme-engines.md`](../research/research-2026-11-01-theme-engines.md)。三条：

### 2.1 「只换颜色」是全行业通病

星数最高的三家，主题引擎都**只能表达单词级属性**：doocs/md（13.5k★）主题是 CSS 但只有 3 套；
md-wechat（256★）28 套；MDskill-Web（165★）33 套但声明了 4 个结构钩子**一个都没用**。
**没有任何一家做出了"整篇版式 × 主题"的二维模型。** 这一层没有现成可抄。

### 2.2 md-wechat 找到了结构层的最小形态 —— **结构钩子**

`laogou717/md-wechat`（MIT）给每套主题留了几个"口子"，渲染器一行接出来：

```js
// src/lib/renderer.js L811
const wrap = styles[`h${level}WrapOpen`] || ''      // ← 在标题文字前后注入 HTML
return `<h${level} style="${style}">${sectionIndex}${wrap}`
```

| 钩子 | 28 套里的使用率 |
|---|---|
| `h2WrapOpen` / `h2WrapClose` | **21 套** |
| `h1WrapOpen` / `h1WrapClose` | **17 套** |
| `hrHtml`（分隔线换成任意 HTML，如 `· · ·`） | **15 套** |
| `h2Index`（`01 标题` 拆成大编号） | 3 套 |

**四分之三的主题靠钩子做出了结构差异。** 这是本方案第 2 层的直接来源。

### 2.3 它还写清了公众号的禁区（我们必须照办）

> 安全区：内联样式、渐变（配纯色兜底）、box-shadow、border-radius、letter-spacing、flex。
> **禁区：`position` 定位、`<style>`、动画、百分比偏移。**

以及一条我们踩过但没写进文档的：

> 微信会识别 `ul/ol/li` 并执行自己的"列表化"转换，**嵌套列表会被提升为顶层、层级全丢**。
> 所以要用 `section + 内联样式` 模拟列表。

（我们 `convert_lists_to_sections` 已经这么做，但 `AGENTS.md` 没写"为什么"。
建议补进文档，否则以后有人会"优化"回原生 `<ul>`。）

## 3. 三层模型

```
长相 =  皮肤 Skin      颜色 / 字体 / 行距 / 字号      ← 今天的 164 套 JSON，不动
      × 钩子 Hooks     标题编号 / 分隔线样式 / 引用装饰  ← 抄 md-wechat，新增，极少改动
      × 版式 Layout    章节怎么分隔 / 段落是否并排      ← 新增，抄 doocs「主题即代码」的思路
```

| 层 | 解决什么 | 是否需要用户选 | 改动量 |
|---|---|---|---|
| **皮肤** | 颜色、字体、行距 | 在版式卡下方点色点 | 0（已有） |
| **钩子** | 「标题带 01 编号」「分隔线是 `· · ·`」「引用带引号」 | 否，**随皮肤自动** | 每套主题加 1–3 个字符串字段 |
| **版式** | 「章节是否分节」「段落是否并排」「首屏放什么」 | 是，点版式卡 | 每个版式一个 Python 函数 |

**为什么三层而不是两层？** 钩子做不出双栏（`h2WrapOpen` 没法把两个 `<p>` 并排）；
版式做不出"这条下划线换成 `· · ·`"这种细节，而那恰恰是很多人一眼就想改的。

## 4. 版式层：原有 8 个一个不丢，合并重复后 8 → 12

### 4.1 原有 8 个版式的去向（逐条，一个都不删）

`STATE.md` 记的 8 个版式是：默认 / 图文节奏 / 卡片流 / 目录导航 / 杂志分栏 / 首屏 / 卡片组 / 时间线。

| # | 原有版式 | 引擎实现 | 本版去向 |
|---|---|---|---|
| 1 | 默认 | 无（直出） | **保留**，仍是默认 |
| 2 | 图文节奏 `rhythm` | `_layout_rhythm` | **保留**（加速：见 §4.3） |
| 3 | 卡片流 `cardflow` | `_layout_cardflow` | **保留** |
| 4 | 目录导航 `outline` | `_layout_outline` | **保留** |
| 5 | 杂志分栏 `magazine` | `_layout_magazine` | **保留** |
| 6 | 首屏 `hero` | `_wrap_hero_sections` | **保留**，与新增「大字刊头」合并为**一个卡的两个变体**（都靠首屏，差别只是首屏有无大图/大字号） |
| 7 | 卡片组 `card` | `_wrap_card_sections` | **保留**，与「卡片流」合并为**一个卡的两个密度变体**（原有两套实现就是同族，见下） |
| 8 | 时间线 `timeline` | `_wrap_timeline_sections` | **保留** |

**合并的两处（这就是"合并重复项"，不是删功能）：**

- **卡片组 + 卡片流**：两者都是"每个 h1/h2 小节独立成卡"，差别只是
  `card` 带阴影边框需主题配置、`cardflow` 只靠底色圆角。合并成 **「分节卡片」** 一张卡，
  卡上给一个 **密度三档**（描边 / 浅底 / 无框）。用户看到的是一个概念，引擎里两套实现都保留，
  按密度选，**行为与今天逐字节一致**。
- **首屏 + 大字刊头**：`hero` 是"首个 h1+段落做成深色首屏"，大字刊头是"首屏只有一句话且字号拉大"。
  合并成 **「首屏」** 一张卡，给 **大字号开关**。

### 4.2 新增 4 个版式（配方来自仓库内 `references/layout-recipes.md`）

| 版式 | 配方 | 结构 | 为什么它和现有的不一样 |
|---|---|---|---|
| **刊头版** `masthead` | M01 Magazine Issue Cover | 期号栏 + 栏目名 → 衬线大标题 → 斜体导语 → 署名行 → 章节号+标题；引用升级成横贯整宽的斜体大字 | 现有 8 个都**没有刊头**（期号/栏目/署名），首屏 `hero` 只有大标题+段落 |
| **侧边栏** `marginal` | M11 Marginalia Essay | 左侧 64px 窄栏放章节编号 + 英文标签，右侧一条发丝竖线隔开正文 | 现有版式**没有真正的左右栏**（`magazine` 是两列正文，不是边注栏） |
| **双栏对照** `split` | M03 Editorial Essay Split / S02 | 正文段落**成对并排**（微信兼容用 `table` 模拟），中间发丝竖线；金句走整宽色带 | `magazine` 是全篇双栏流水；这个只把**成对段落**并排，其余整宽 |
| **编号塔** `bignum` | S09 KPI Tower / M12 | 每节以 44px 等宽大编号开篇 + 横贯分隔线；清单带方形序号块 | 现有 `outline` 是目录列表，不是"每节一个大编号" |

> **共同前提（必须遵守）**：所有版式不写死任何颜色，全部从 `theme.colors` 派生。
> 反例教训：`_wrap_hero_sections` 曾写死 `#ffffff`，暗底主题直接不可读。

### 4.3 顺带修的两个既有缺陷（这是"更好的引擎"的具体内容）

| 缺陷 | 现状 | 修法 |
|---|---|---|
| `_layout_rhythm` 用正则改 `<p>` 的 `margin-bottom` | `re.sub(r'(<p[^>]*style="[^"]*?)margin-bottom:[^;"]*', ...)` —— 只要 `<p>` 没有 style 属性就**完全不生效**，等于静默失效 | 改用与 `_layout_magazine` 同款的深度感知分块器 |
| `_layout_outline` / `_layout_cardflow` / `_layout_magazine` 都各自写了一遍"按 `<h[12]>` 切节" | 三份重复逻辑，改一处漏两处 | 抽成 `_split_sections(html)` 单一真源 —— **纯重构，输出字节不变**（用 §10 的 dump 脚本 diff 验证） |

## 5. 交互：颜色在版式卡下方点选

用户的原话是「重复的更改颜色的话，就在下方点选颜色更改就行」。落成：

```
风格库抽屉（沿用现有 #drawer，宽 560）
┌──────────────────────────────────────────────┐
│ 风格库   [搜名字或 id…]                  ×   │  ← 现有 drawer-head，不动
├──────────────────────────────────────────────┤
│ 版式                                          │  ← 新增版式层（现有 .drawer-layouts 升级）
│ [默认][首屏][分节卡片][图文节奏][目录][杂志]   │
│ [时间线][刊头][侧边栏][双栏][编号塔]           │  ← 12 个胶囊，两行放得下
├──────────────────────────────────────────────┤
│ 版式预览卡（当前选中版式的大预览）             │  ← 新增：让用户看到结构
│  ┌────────┐                                   │
│  │ 骨架图  │ 刊头版                           │
│  └────────┘ 期号+栏目 → 大标题 → 导语 → 署名   │
├──────────────────────────────────────────────┤
│ 配色   ● ● ● ● ● ● ● ● ● ● ● ● …            │  ← 色点在版式卡下方
│        （按族分组，点一下就换，结构不动）       │
├──────────────────────────────────────────────┤
│ 段落样式  ☑金句  ☑数据  ☑提示                  │  ← 现有 drawer-blocks，不动
│ 自定义配色 [底色][正文][强调]                  │  ← 现有 drawer-custom，不动
└──────────────────────────────────────────────┘
```

**为什么色点在抽屉里而不是全屏弹窗**：现有抽屉已经有「选模板不关闭、可连续对比」
（`body.browsing` 让位 500px，预览在左边实时变）。改成全屏弹窗会打断这个"连续对比"，
而这正是 2026-10-27 特意做对的地方，不能退回。

**顺带的收益**：164 个色点按 **7 个族分组**（公文 12 / 信笺 12 / 暮色 10 / 夜航 12 / 节庆 12 / 钢印 12 / 素页 12 + 经典 82），
每组 12 个色点占约两行 —— 用户不必再面对"164 个名字"。

## 6. 皮肤层：164 套怎么变少而不丢

不改任何一套主题 JSON，只在**索引层**加一步分组：

| 现在 | 改后 |
|---|---|
| 164 张卡，79% 有"长得一样的兄弟" | **49 个"设计签名" → 49 张父卡**，同签名的 12 套收进父卡的色点行 |

父卡的代表 = 该签名组里 `theme-curation.json` 排最前的那一套。
**所有 164 个 id 全部可达**（色点点击即选中该 id），收藏 / localStorage / 测试零影响。

### 7.1 两条必须补的产物级断言

1. **版式真的不一样**：同一夹具 × 同一皮肤，跑两个版式，导出的 HTML
   **结构指纹必须不同**（比 `<h2>` 前面的兄弟节点结构，不比像素）。
   反向验证：把版式函数换成 identity，这条必须**失败**。
2. **钩子真的生效**：同一皮肤开/关 `h2Index`，`<h2>` 内必须出现编号 `<span>` 且原文标题文字不丢。
   反向验证：把钩子读成常量 `''`，必须失败。

## 11. 明确不做

| 不做 | 原因 |
