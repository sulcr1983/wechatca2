## 一、竞品的架构（与我们的根本差异）

```
它：  顶栏（粘贴/导入/配图/导出/复制） + 三 tab（编辑 | 预览 | 设置）
我们：顶栏（导出/AI/更多）           + 双栏（内容 | 预览） + 底部风格条
```

### 它把「设置」独立成 tab，并分三类

| 分类 | 内容 |
|---|---|
| **设计** | 排版风格（4 款）· 文章配色（3 组）· **背景风格（4 款）** |
| **文字** | **正文字号滑块（14–18px）** |
| **内容** | 首段作为导语 · 显示链接网址 · 预览公众号标题 · **标准页尾** |

### 它写在界面上的两条设计哲学（可直接引用）

> **「只改变配色，不改变排版结构。」** —— 文章配色
> **「独立选择背景，与排版和配色自由组合。」** —— 背景风格

这是**正交性声明**：明确告诉用户这几个维度互不影响。

## 二、A 档（用户已定：全做）

### A-1 标准页尾 ★ 对应上一轮「结尾预设」需求

**竞品实现**：
```
☑ 附加页尾内容
  独立于正文，自动附在末尾。支持 Markdown。
  ┌──────────────────────────────────────┐
  │ **关于作者**                          │
  │ 专注工程仿真与 AI 技术发展趋势分析…    │
  │ **如果觉得有价值，请点赞、分享或收藏。**│
  └──────────────────────────────────────┘
  设置在本机保存，复制和导出包含页尾。
```

**四个要点**：
1. **支持 Markdown**（不只是纯文本）→ 可以写 `**加粗**`、列表
2. **本机保存**（localStorage）
3. **复制和导出都包含**
4. 明确「**独立于正文**」

**它只做页尾，没做页头。** 我们上一轮定的「开头 / 结尾 / 通用块」比它全面，
但**第一版建议先做页尾**（对齐竞品，验证可行后再扩）。

**我们的落点**：
- 存储：`supersu.snippets`（新建，`supersu.` 前缀已被 `clearAll()` 覆盖）
- 渲染：`doRender()` 取文本时拼接 `正文 + '\n\n' + 页尾`
- 引擎零改动（页尾是 Markdown，走同一条 `preprocess → format_engine` 路径）

### A-2 显示链接网址

**竞品文案**：
> 「公众号不支持的外部链接，保留网址供读者查阅。」

**作用**：公众号会剥离 `<a href>` 的外链跳转，用户读不到 URL。
开启后，在链接文字后面补一个明文 `(https://...)`。

**我们的落点**：`core/format_engine.py` 的 `md_to_html` 出口，
对 `<a href="http...">text</a>` 追加 `<span>（网址）</span>`。需要开关控制。

⚠️ **注意**：这会改变 164 套主题的渲染产物（只要开了这个开关），
必须做成**默认关闭**，且进了开关才生效。

### A-3 导出说明文案

**竞品文案**：
> 「长图包含正文、配图、背景和页尾，不包含工具栏。GIF 将导出为静态画面。」
> 「在当前浏览器生成，无需上传正文。」

**我们的现状**：导出菜单只有 4 个选项 + 一行小字用途（「朋友圈 / 小红书」「留档 · 交稿」…），
**没有说明「包含什么、不包含什么」，也没有隐私声明**。

**落点**：`pwa/index.html` 的 `#menu-export` 加一行说明 + 一行隐私声明。纯文案。

### A-4 主题卡片加气质描述

**竞品**：
```
┌────────────────────────────┐
│ 技术编辑        当前使用 ✓ │
│ 清晰层级 · 克制留白        │  ← 一句话气质
└────────────────────────────┘
```

**我们的现状**：164 套主题的 `desc` 字段**已经存在**（`themes/index.json` 里有），
但抽屉卡片只显示 `name`，不显示 `desc`。

**落点**：`drawerCard()` 加一行 `desc` 截断（约 20 字）。
⚠️ 卡片高度会从 140px 增至约 160px，需要同步调 `.d-card` 与网格。

## 三、B 档（用户已定：全做，且明确「字号铁律可以改」）

### B-1 背景风格独立

**竞品四款**（与配色**正交**，可任意组合）：

| 纯白 | 暖纸 | 纸张纹理 | 细网格 |
|---|---|---|---|

**为什么我们没有**：`background` 写死在主题 JSON 的 `colors.background` 里，
选主题就锁定了底色。

**落点**（`core/format_engine.py` 第 8.1 步，实测行号 L2407–2418）：

```python
if "wrapper" in style_map and not skip_wrapper:
    if theme.get("layout") == "card":
        ...
        wrapper_s = f'padding:40px 10px;background-color:{card_bg};...'
    else:
        html = f'<section style="{style_map["wrapper"]}">{html}</section>'
```

**改法**：新增一个 `theme["background_override"]` 字段（或显式参数），
在生成 `style_map["wrapper"]` 之前覆盖 `background-color`。

**风险**：
- 影响 164 套主题（但只在用户主动选背景时生效）
- 纸张纹理/细网格需要 `background-image`（base64 内联小图 或 CSS 生成）
- 与「整篇设计（kit）」冲突：kit 的背景是设计的一部分，应该**禁用**背景覆盖

**建议做法规避**：用 `background_override` 显式参数，**不改**主题 JSON。
这样 164 套主题产物零变化（回归可验证：不传该参数时字节一致）。

### B-2 正文字号滑块（14–18px）

**竞品**：
```
正文字号  [====|=====] 15 px
14–18 px，预览与复制同步生效。
```

**用户明确**：「AGENTS 里有铁律『字号只改 SCALE 一处即全量生效』，**这个铁律可以修改的。不应该成为铁律**。」

所以：

- **原铁律的合理部分保留**：改 `SCALE` 重跑 `build_themes.py` 仍是**批量改主题**的正路
- **新增用户级覆盖**：运行时允许单篇调字号，**存本机，不改主题 JSON**

**落点**：`core/format_engine.py` 里 `p` 的字号来自 `theme["styles"]["p"]["font_size"]`。
加一个 `font_scale` 参数，在 `inject_inline_styles` 构建 `style_map` 时对 `p` 生效。

**风险**：只改 `p` 还是连带 `list_item_text` / `blockquote_p` 一起？
竞品只写了「正文字号」，建议**只改 `p`**，其他保持主题原样。

### B-3 首段作为导语

**竞品文案**：
> 「用浅色背景突出完整的开篇段落。」

**效果**：第一段（标题之后的第一段正文）自动加浅色背景块，做「导语/摘要」视觉。

**落点**：`core/format_engine.py`，在 `inject_inline_styles` 之后对**第一个 `<p>`** 加样式。

**风险**：如果文章第一段很短（比如一句话），加背景会显得突兀。
建议加长度门槛（如 ≥40 字才触发），或做成开关由用户控制。

### B-4（用户补充）新增 4 套背景与 15 套独立放置

> 用户原话：「其次是新增的四套可以和之前是15套独立的一起放置。」

**理解**：背景风格（4 套）应当**与 15 套整篇设计平级**，都是「独立可选项」，
不塞进「配色主题」的次级参数里。

**落点**：抽屉的 tab 结构可能是：
```
[配色主题 164] [整篇设计 15] [背景 4]   ← 三个并列？
或
[配色主题 164] [整篇设计 15]
                 └ 背景风格作为整篇设计的下级？  ← 不推荐
```

⚠️ **这一条需要用户确认具体摆法**（见 §五）。

## 八、新增需求：自动配图技术（用户 2026-11-02 追加）

> 用户原话：「自动配图的那个技术也要同步研发，记录在技术文档里面。」

### 8.1 竞品的「添加配图」是什么

实测 md2wechat 的「添加配图」按钮：点击后**跳到编辑区**，没有弹窗。
设置面板底部有一句说明：

> 「添加本地图片后自动插入引用。图片是否随正文进入公众号，仍需在微信中确认。」

**它的做法很朴素**：上传本地图 → 在 Markdown 里插入引用语法 → 不保证能进公众号。

**注意「仍需在微信中确认」这句** —— 它自己也不确定图片能否随正文进去。
而我们的项目**已经实测确认过**（`cd0668d` 前 / 2026-11-01 用户实测）：

> **公众号接受 `data:` URI 内嵌图。**（`docs/engine/design-paste-image-and-typography.md` §3.3）

**所以在这一点上我们是领先的** —— 我们的 `editor-images.js` 已经做到「粘贴/上传 → 压缩 → data URI → 复制时内嵌」。

### 8.2 我们已有的配图能力（实测，`pwa/src/`）

| 能力 | 实现 | 状态 |
|---|---|---|
| Ctrl+V 粘贴截图 | `editor-images.js` | ✅ 已完成 |
| 「插图」按钮上传 | `handleImageFiles` | ✅ 已完成 |
| 搜图（Pexels BYOK） | `bindPicDialog()` | ✅ 已完成 |
| AI 生成英文关键词 | `ai.js` 的 `suggestImageKeywords()` | ✅ 已完成 |
| 复制时自动内嵌外链图 + 压缩 | `copyRich()` → `localizeImages({compress:true})` | ✅ 已完成 |
| 图片 ZIP 导出 | `export.js` 的 `exportImages` | ✅ 已完成 |

来源：`docs/meta/open-tasks-2026-11-01.md` §1（I-1 到 I-7 全部已完成）。

### 8.3 缺口：真正缺的是「自动」两个字

现有能力都是**手动触发**（用户点按钮）。「自动配图」要的是**系统自己判断在哪插图、插什么图**。

#### 三种可能的自动化程度

| 级别 | 行为 | 难度 | 风险 |
|---|---|---|---|
| **L1 自动定位** | 分析文章结构，建议「这里适合放一张图」并高亮 | 低（纯规则） | 无 |
| **L2 自动搜图** | 按小节关键词自动搜图并预填，用户确认/更换 | 中（要 Pexels Key） | 搜错图 |
| **L3 全自动插入** | 直接插入并内嵌，用户事后调整 | 高 | **高风险：图不贴题比没图更糟** |

#### 我的判断：**先做 L1，L2 可选，L3 不做**

理由：
1. **L1 零依赖**：纯规则判断「哪些位置适合配图」，不联网、不要 Key
2. **L2 依赖用户 Key**：没 Key 的用户直接不可用，且搜图质量不可控
3. **L3 违背项目定位**：`AGENTS.md` 写着「纯文本进，排版出」「不用 AI 就不开 AI」，
   全自动插图属于「AI 主动创作」，不是「排版」

### 8.4 L1 的实现思路（纯规则，零依赖）

**判断「哪里适合插图」的确定性规则**（与 `preprocessor` 的「只做确定性识别」一致）：

| 信号 | 规则 |
|---|---|
| 小节开头 | 每个 `##` 标题后的第一段之后（若该节 ≥3 段） |
| 长段落之后 | 连续 ≥4 段正文后 |
| 列表之前 | 一个 ≥5 项的列表之前（图 + 列表是常见组合） |
| 数据密集处 | 一段里有 ≥3 个数字/百分比 |
| 文末 | 正文结束后（可放签名图/二维码） |

**输出**：不直接插图，而是在编辑器里显示**灰色占位提示**：
```
┌─ 建议在这里配一张图 ─────────┐
│ 本节讲「海边日落」，可搜「日落」│
│ [搜图] [上传] [忽略]          │
└───────────────────────────────┘
```

**关键：不静默插入。** 符合项目铁律「每个降级说明原因、不静默」。

### 8.5 需要新增的技术点

| # | 技术点 | 落点 | 依赖 |

- **AI 生成关键词** → 已有（`suggestImageKeywords()`），但要用户配 Key，属可选增强
