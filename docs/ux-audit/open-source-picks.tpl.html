开源方案选型：每个问题先找现成的轮子

纪律：能用成熟开源就直接用，不手写半成品。下面把审计后确认的问题逐个对到具体的开源项目/库，标明「直接引入 / 抄算法 / 抄交互 / 仅参考」，附出处。

选型总结（一句话版）：

  • 封面标题溢出 → 直接引入 fitty（零依赖、两套引擎模板通用，本周就能上）
  • 选模板难 → 抄 md-wechat 的「悬停即试看」交互 + 自研「最近使用置顶」（很小的工程）
  • 排版主流程体验 → 对齐 doocs/md（12.5k★）的成熟范式，不替换自研引擎
  • 封面渲染去浏览器化（中期） → 试点 satori（Vercel 官方），甩掉 Chromium/Node 依赖
  • 进度反馈 / 搜图缓存 / 记住上次主题 → 无现成轮子，自研（都是小工程，不值得为此引依赖）

02重点展开三个「直接能用」的

① fitty：一个文件，同时治两套封面引擎的标题溢出

审计已实锤：溢出根因是两套引擎的封面模板写死字号（BLCaptain .sp-display{font-size:76px}，归藏同理）。 fitty 干的就是这一件事：把单行文字缩放到正好塞满父容器，零依赖、支持最大/最小字号、内容变化自动重算。

落地方式（两套引擎通用）：封面模板是 HTML，只需引入 <script src="fitty.min.js"></script> 并在标题元素上调用 fitty('.sp-display', { minSize: 40, maxSize: 76 })——标题长就自动缩、短就保持大字号。归藏引擎同理对它的标题类调用一次。 ⚠️ 纪律提醒：BLCaptain 是 vendored 子项目，改模板源后要重新生成 + 跑它自带的 .mjs 测试。
为什么选它而不是自己写缩放：fitty 处理了 web 字体加载时机、DOM 读写合并性能、窗口变化监听这些自己写必踩的坑；MIT 协议、一个 min.js 文件，拷进模板即可，没有供应链负担。

② md-wechat 的「悬停即试看」：治「92 个模板挑花眼」的最便宜解

我们审计时推翻了「给 92 套主题人工打标签」——成本高、标签还容易打歪。md-wechat 给出了更聪明的答案：鼠标悬停在主题卡上，右侧预览立刻换装。选错的成本变成零，根本不需要分类。

落地方式：我们已有 /api/render（输入主题 id 秒出 HTML），把「点击才渲染」改成「悬停 200ms 防抖后渲染预览」即可，后端零改动。配合「最近使用 3 套置顶 + 收藏」（localStorage 记录），常用的永远在前排。
为什么更省事：不逼用户「想一个分类词」，扫一眼效果就定了；人工打 92 个标签的一天工作量，换成悬停试看半天就能上线。

③ satori（Vercel 官方）：封面渲染「去浏览器化」的中期路线

现在生成一张封面 = Playwright/Node 冷启动 + 浏览器渲染截图（慢，也是之前「封装 exe 要 500MB」的元凶之一）。 satori 用纯 JS 的 Flexbox 引擎（React Native 同款 Yoga）把「样式描述」直接算成 SVG，再转 PNG——全程没有浏览器，Vercel 用它给数百万站点动态生成 OG 图。

能力边界（选型前必须知道的）：支持 Flexbox、渐变、圆角、边框、阴影、图片（base64）、文字溢出省略；不支持 CSS Grid、伪元素、动画、calc()；中文字体需显式加载字体文件。复杂视觉模板迁移前要先对着这个清单过一遍。

定位建议：不作为本轮 UX 修复的前置项。正确节奏是——先上 fitty 止血（本周），交互对齐 doocs/md；若后续确认要减依赖/提速/瘦身分发，先拿 1 套 BLCaptain 模板做 satori 试点，跑通「同模板双实现」对比视觉一致性，再决定是否全面迁移。

为什么现在不急着上：迁移 9 套模板有真实工作量，且视觉细节有降级风险；而 fitty + 缓存已能解决「溢出」和「慢」这两个当下最痛的点。先用小轮子止血，大轮子等验证。

03诚实的边界：哪些没有现成轮子，自研是对的

以下几项搜了一圈没有对口开源组件（它们是业务逻辑而非通用能力），自研几行代码反而比引依赖更省：

  • 阶段化进度反馈（找底图 → 排版 → 完成）：前端几个状态切换；
  • 搜图缓存：按关键词落盘缓存（项目已有 data/bg_cache 目录雏形），补 TTL 即可；
  • 记住上次主题 / 最近使用置顶：localStorage 读写；
  • 署名如实显示（local 时写「联网没找到，已用本地底图」）：改一行模板字符串。
判断标准：通用能力（文字缩放、DOM 转图、布局引擎）→ 找成熟库；业务小逻辑（缓存、记忆、文案）→ 自己写。反过来就是灾难：为「记住上次主题」引一个状态管理库，才是真正的过度工程。
