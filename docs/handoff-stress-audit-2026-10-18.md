## 0. 三分钟看懂这个项目

**SuperSu** 是苏哥的个人工具：纯文本进 → 公众号排版出，再带一个小红书封面生成。核心理念是"不用 AI 就不开 AI"。

它有两个发行形态（新人最容易踩的坑就在这）：

| 形态 | 入口 | 引擎跑在哪 | 怎么验证 |
|------|------|-----------|----------|
| 本地 Flask 端 | `python app.py` → http://127.0.0.1:5000 | 服务端 Python | 本地浏览器 |
| 线上 PWA 端 | https://supersu.ccwu.cc | 浏览器内 Pyodide 跑同一套 Python | 系统 Chrome 有头 |

两者**共用** `core/preprocessor.py`（纯文本→Markdown）和 `core/format_engine.py`（Markdown→微信内联 HTML），主题 JSON 也共用 `public/themes/`。**改引擎代码要两边一起验，否则"本地修好了线上没变"**（审计报告 P1-8 指的就是这个）。

## 2. 本次实测发现的真问题（按优先级）

### P0 — 必修（影响"原文不丢"这条底线）

**P0-1 · 原文保真：标签行冒号被吞、有序列表序号被改写（H01 FAIL）**
- 现象：测试夹具里 `另一种无序列表：`、`脚注测试：` 这类"标签行"被预处理剥掉了结尾冒号；`2. 第二阶段：排版` 这类有序项被统一重排成 `1.`。
- 影响：违反测试夹具明写的"不要擅自改写事实或丢失原文"。视觉上多数无碍，但属于"悄悄改字"。
- 根因：`core/preprocessor.py` 的"短标签行 ≤9 字+冒号结尾"规则、`有序列表` 重排规则。
- 修复方向：标签行保留冒号；有序列表只在"确认为列表"时才重排，否则原样保留序号文字。

**P0-2 · 分隔线被当成标题：冒出 32 个「## =」（S02 FAIL，视觉灾难）**
- 现象：测试夹具每章用 `============` 分隔，`preprocessor` 的装饰标题正则把纯分隔线判成 `## =`，全文档产生 32 个假标题。
- 影响：预览里一堆"="标题，目录层级全乱。
- 根因：`_DECORATED_TITLE_RE` 没有排除"中间只有等号/无内容"的行；`_UNDERLINE_RE` 也把纯分隔线当 setext 下划线，把上一行升级成标题。
- 修复方向：纯分隔线（`^[=＝\-—]{3,}$` 且不含其它字符）一律原样透传或当 `<hr>`，绝不该产出标题。

### P1 — 该修（结构误判，教程 / 清单 / 数据类文章会崩）

| 编号 | 问题 | 现象 | 对应审计条目 |
|------|------|------|------|
| P1-1 | 标准有序列表被转成标题（S11 FAIL） | `1. 导入 TXT`…`5. 复制到公众号` 全部变成 `## 1. 导入…`，教程步骤的层级崩溃 | 审计 P1-1 |
| P1-2 | 嵌套列表层级丢失（S12 FAIL） | `- TXT 文件` 等二级项缩进被抹平，6 个子项 0 个保留缩进 | 审计 P1-1（缩进分支） |
| P1-3 | 竖线表格误判为标题（S17 FAIL） | `功能 \| 难度 \| 说明` 这类非标准表格被当标题 | 审计未单列，但属同类 |
| P1-4 | 数学公式块被标题化（S20 FAIL） | 独立公式 `$$ … $$` 变成 `## $$` | 审计未单列 |
| P1-5 | 加粗被破坏（H03 FAIL） | 原文 `**先保证原文不丢…**` 被 `*` 项目符号规则剥成 `- *先保证…**`，既丢加粗又多一个列表项 | 保真问题 |
| P1-6 | 原始 HTML 片段被标题化（H06 FAIL） | 测试夹具第 15 章 `<div class="notice">`、`<br>` 被当标题；且与下面 P2-4 安全项叠加 | 审计 P2-3（部分） |
| P1-7 | 8 套主题对比度不达标 | `sakura / sunset-gold / sunset-blend / autumn-leaf / morning-dew / soft-paper` 正文/背景对比度 < 4.5:1；`sunset-amber / wechat-native` 代码块对比度 < 4.5:1 | 审计 P2-2（可读性） |

> P1-1/P1-2 是审计报告反复强调的"确定性边界问题"，优先级最高——它们直接打脸"教程型文章"这个核心场景。

### P2 — 体验（重复感 / 字号 / 诗词 / 安全）

- **P2-1 模板重复感**：见第 3 节量化证据。
- **P2-2 字号过大观感**：见第 4 节，建议保留 15–16px。
- **P2-3 诗词未分层**（S22 FAIL）：`静夜思`/`李白` 没被识别成标题或诗词块，与正文混排。文档只要求"可采用不同层级"，属可改进项。
- **P2-4 HTML 安全加固**（H06 关联）：用户输入含 `<script>`/事件属性的 HTML 片段时，当前会被原样透传进渲染 HTML（测试夹具的 `<div class="notice">` 已出现）。**未实测可不可执行，但这是审计 P2-3 点名的安全加固点**，上线前必须加白名单清洗 + 危险 URL 拦截。

## 3. 模板"重复感"量化证据与治理建议

**苏哥原话**：模板太多、重复太多、很多通不过测试。要么改、要么删、要么折叠。

### 量化证据（本次实测）
- 164 套主题里只有 **61 个真正不同的骨架**（字号/字重/间距/圆角/标题气质/引用样式）。
- **最大同构组 26 套**——也就是 26 套长得几乎一样，只差颜色。
- 第二批"六族 × 十二色"共 72 套，其中 **6 个族各 12 套完全同构**（biz / letter / minimal / night / stamp + 还有一族），合计 72 套 = 纯换色模板。这正是"44% 同模换色"的来源。
- 另有 **4 对**主题背景色 ΔLab < 12、强调色 ΔLab < 18，肉眼几乎分不出来（如 `su-brushink` 与 `su-quietdoc` 背景 ΔE=0）。

### 治理建议（含对抗性审查）
> 先自问：治本到底是"删主题"还是"界面归类"？

| 方案 | 做法 | 优点 | 风险 | 结论 |
|------|------|------|------|------|
| A 直接删重复 | 删掉近重复组，只留代表 | 主题数骤减 | **删 `su-*` 生成物违反"只改 spec 不手删 JSON"的铁律**（见 `AGENTS.md`）；且删了用户可能喜欢的配色 | ❌ 不推荐，易误删、难追溯 |
| B 界面折叠 | 同族 12 个换色 → 1 个代表 + 色相选择；按文章类型给 6–8 个精选入口 | 视觉从 164 变几十组、不丢资产、可一键展开全部 | 老用户习惯全铺开，需保留搜索/展开 | ✅ **推荐** |
| C 精简生成器 | 在 `scripts/theme_specs.py` 减少"纯换色"族，重跑 `build_themes.py` | 从源头减少同构 | 需重新生成 + 重做缩略图 + 回归 | ⚠️ 可后续，但先于 B 做会动资产 |

**推荐路线：先 B（界面折叠 + 文章类型推荐），再视反馈做 C。** 不删任何现有主题，只改 `templates/index.html` 的模板库抽屉（现有 `#tpl-strip` / 家族 chips 已支持扩展折叠），并在"同族"下挂色相选择。

## 4. 字号调研结论（苏哥问的"正文改 13、标题 15 会不会更好"）

**先纠正一个事实**：不是"现在都是 15 号"。实测 164 套里正文 **16px × 121 套、15px × 43 套**，标尺基准（`scripts/build_themes.py` 的 `SCALE`）就是 16px。标题 h1 多在 25px、h2 在 20px。

**行业共识（联网调研，2026-10-18）**：

| 来源 | 正文字号建议 | 标题 | 结论 |
|------|------------|------|------|
| 135 编辑器 | **14–16px，强烈推荐 15px** | — | 别用 12/10px |
| 有一云 | 15px 万能；14px 文艺；16px 资讯科普 | 一级 18–22、二级 16–18 | 正文别低于 14 |
| 话媒盒子 | "**不要用 14px，太小了**"，15/16 最舒服 | 小标题 18/20 | 强调正文一种色、加粗是唯一强调 |
| 吉加设计 | 15–16px | 大标题 22–24、小标题 18–20 | — |

**结论与建议**：
1. **不建议把正文降到 13px**。13px 在手机上偏小，行业明确把 13px 划进"注释/引用"层级（10–14px），不是正文。正文降到 13 会让中老年读者吃力（公众号用户年龄偏大）。
2. **"感觉字太大"更可能是预览观感问题，不是真实手机效果**。预览用的是 `phone-shell` 375px 手机框，16px 在 375px 宽里就是真实手机效果（合适）；若苏哥是在电脑大屏上看这个窄框，16px 会显得"顶满"，这是**框小字大**的错觉，不是字号错。
3. **真要调，建议只动"间距/行高"而非字号**：把 `SCALE` 的 `p` 从 16 微调到 **15**、行高保持 1.9，比降到 13 更稳妥。或给预览加一个"实际手机 375px 缩放"的明确对照，消除错觉。
4. **标题 15px 不合理**：现行 h2 已经 20px，降到 15 会让标题/正文区分度不足。标题保持 18–22px 区间（行业一致）。

> ⚠️ 字号是产品观感决策，本文只给数据和建议，**最终由苏哥拍板**（见第 7 节决策清单）。改动点在 `SCALE` 一处，重跑 `build_themes.py` 即全量生效，可逆。

## 5. 红线（绝对不能做）

1. **不抄任何开源主题/代码**。xiaohu-wechat-format 已明确否决（见开源方案 §9 核查：其仓库无 LICENSE 文件，且我们 164 套已覆盖其能力）。gzh-design-skill 是 AGPL，**一个字节都不能进代码树**。
2. **不重写架构**。审计报告结论是"先修解析与编排，不要重写架构、不要换模型"。
3. **AGPL 来源资产不进公开 PWA 构建产物**（项目自定规矩，红线 1）。
4. **不手删 `public/themes/*.json` 的 `su-*` 生成物**——它们由 `build_themes.py` 从 `theme_specs.py` 生成，要减就改 spec 重跑。
5. **先统一许可证再说分发**：线上"关于"标 AGPL-3.0，但仓库 README 的 License 段**已为 AGPL-3.0**（2026-10-18 核实），根目录 `LICENSE` 是 AGPL-3.0 全文、`THIRD_PARTY_NOTICES.md` 存在——口径已一致（审计 P0-1 已 PASS）。本条原描述（README 写的是 MIT）是过时信息，无需改动。

### 9.3 字号定稿（取代 §4 的"建议不动"）
