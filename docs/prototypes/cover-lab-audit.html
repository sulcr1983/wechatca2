对抗性审计：结构加对了，
视觉和数量判断都错了

立场：假设这版原型全是错的，逐条去代码和实测里找反证。找得到就认，找不到才保留。
审计对象：docs/prototypes/cover-lab.html　追加约束：现有优势不可丢（联网底图 / 归藏风格）、模板数量是核心资产。

审计总评：算法层（拆页 / 断行 / 自适应）站得住，视觉层是倒退。共 3 处推翻、1 处致命盲区、3 个真 bug，也保下 4 条真增量。其中裁定 3 又被「模板要多」这个定位二次推翻（见 §01 末）。

最重的一条：原型在字重、字距、字体三件事上，正好踩了项目 references/style-system.md:34 明确标注的反面教材。你一句「归藏好看的风格不能丢」，眼睛是对的，我把它写成了代码级证据。

审计后最重要的一句话：这版原型的价值在证明结构可以组合 —— 而结构可组合，正是「模板更多更齐全」的产能来源。它缺的不是方向，是把视觉质量接到归藏规范上。数量靠正交，质量靠规范，两件事不冲突。

01被推翻的三条

裁定 1：我说「现有是 12 套扁平主题」—— 没读代码就下结论

推翻

上一份调研里我断言「12 套扁平主题，加一套要复制整个 HTML」，并以此作为「正交化重构」的主要理由。去读 pwa/src/cover/templates.js 才发现这个判断是错的。

证据：templates.js:23-41 有 GZ_COLORS（paper / paper2 / ink / muted / accent / accentSoft / bg 7 个槽位），:48-59 有 GZ_FONTS（family / titleSize / weight / tracking / bodySize 5 项）。颜色与字体早已分离成两层参数，这正是「正交」的雏形。真正扁平的只是 public/cover-templates/ 那 10 套独立 HTML（66–177 行/套）。

修正：正交化不是「从零重构」，而是把已经参数化的两层往下推到 10 套模板。工作量比上一轮估的低，但前提是——不许动那套参数的取值（见裁定 2）。

为什么这条重要：方向没变，但我给的理由是假的。用假理由推真方案，一旦遇到质疑就会站不住。

裁定 2：原型的排版规范 —— 踩了自家文档的反面教材

推翻

证据（文档）：references/style-system.md:34 原文——「the larger, the lighter … Display titles run at weight 500 with wide tracking (+.03em to +.04em). Body uses serif-zh, not sans. The anti-pattern — 700 to 900 weight display, sans body, negative tracking — collapses Editorial into a generic "infographic banner" look.」
证据（我的代码）：原型 poster 版式 --w-title:800、--tr-title:-.025em；stack 700 / −.02em；list 750 / −.02em；正文全部 PingFang / 微软雅黑 无衬线。反面教材的三条，一条不落全中。

修正：原型的 8 套主题全部作废，不当视觉参考。要复用的是它的结构能力（版式骨架可组合），视觉参数一律从 GZ_COLORS / GZ_FONTS 取。

为什么这条最重：我上一轮把「外部方案」当成先进经验引进，却没意识到项目手里的排版规范比外部更成熟。归藏的 28 版式 / 10 主题是有设计系统支撑的，不是我临时写的 8 组 CSS 变量能比的。

裁定 3：「48 种组合」—— 这条被我自己的下一个前提二次推翻

二次推翻

我原先写的是「做给谁看」：单人用户、已有 164 套主题、真实痛点是选择过载。这个论证的第一步就错了 —— SUPERSu 是开源项目，用户不是一个人，是一群陌生人。把「唯一高频用户」当设计前提，等于把开源产品的核心资产当成负担。

纠正后的定位：模板的数量、齐全度、美观度就是产品本体，不是成本项。所以 48 格不是「过多」，是还远远不够。正交化也不是「省得写模板」，而是产量放大器 —— 同一份规范下，N 风格 × M 版式 能持续生出新模板。

但「选择过载」这件事仍然真实存在。它不该用「减少模板」来解，该用组织方式来解 —— 这恰好也是我上一轮从外部方案里学到的：「试错免费」比「替我分类」更符合真实选择方式。

「多」和「漂亮」怎么同时成立

层做法解决什么
产能风格 N × 版式 M，全部参数化数量。加一套风格只写变量，一天能加十套
质量所有新风格必须从 GZ_FONTS 取字重 / 字距 / 字体配对，不许自创漂亮。防止「加得越多越难看」
分层精选（手调过）／ 可用（校验通过）／ 实验（可试，标灰）选择过载。默认给最好的，想探险也有路
检索悬停即试看 · 气质标签 · 最近使用置顶找到得快。不用想关键词，扫一眼就定
门禁每个组合自动跑：溢出 / 字号区间 / 正文对比度 / 断行 / 安全区不出丑。把 §03 那三个 bug 变成自动拦截

修正：组合矩阵全部保留并扩容，配「精选置顶 + 悬停试看 + 气质检索」三件套。数量要涨，但涨的每一格都得过质量门禁 —— 这是「更多」和「更漂亮」能同时兑现的唯一方式。

为什么这条最该记住：我连续两轮用错了用户假设（先当大众产品、再当单人工具），这次才对准——开源产品：作者是第一个用户，但绝不是唯一用户。凡是拿「我用不着」当砍功能的理由，在这个项目里都不成立。

02一个致命盲区

裁定 4：原型零底图能力，而底图是现有最硬的差异化

盲区

原型 8 套主题全是纯色 + 纸纹。联网搜真图作底图这件事，一行都没进原型。

证据（现有代码已解决）：templates.js:216 applyImage() 负责底图注入与清除；:71-78 的 OVERRIDE_CSS 用 body.has-img 把标题/副标/正文强制成 rgba(255,255,255,.95) + text-shadow:0 2px 8px rgba(0,0,0,.35)，这就是「文字压图可读性」的现行解。core/image_search.py 负责联网找图。

原型完全没验证的，是带图封面的这几个真问题：

  • 文字压在亮部 / 暗部区域时，同一套白字方案是否都成立
  • 遮罩强度该固定还是随图自适应（has-img 目前是固定值）
  • 主体避让：人脸、产品、关键动作附近的字要不要挪
  • 底图的主色与 --accent 撞色时怎么办（inkForAccent() 只解了「墨色该黑还是白」，没解「强调色撞底图」）
  • 拆页时，第二页起要不要重复底图 / 换图 / 纯色
结论：原型只能算「纯色封面」这一支的验证。要落地必须先补一版带底图 + 多页的样张，否则等于拿半个方案去改生产代码。

BREAK_CUES 里放了 '把' '让' '你' '它' 这类单字，会在任意位置命中：

05修正后的路线

处置对象说明
保留拆页 / 语义断行 / 缩略图自检 / 安全区四条真增量，进生产前先修裁定 5–7 的三个 bug
保留版式骨架可组合（结构层）但只组合「骨架」，颜色字体一律取 GZ_COLORS / GZ_FONTS
重写原型 8 套主题的视觉参数主题概念和配色保留，但字重 / 字距 / 字体必须按 GZ_FONTS 规范重写
扩容组合矩阵 → 全量保留并扩张模板数量是开源产品的核心资产。配精选置顶 / 悬停试看 / 气质检索来解选择过载
不动归藏 12 套风格 / 联网底图管线现有视觉上限与差异化。新增风格必须继承其规范，不许另立一套
前置带底图 + 多页样张补这个之前，不许改生产封面代码

如果只做一件事：把归藏的排版规范固化成硬约束 —— 新风格的字重 / 字距 / 字体只能从 GZ_FONTS 取，不许自创。理由：模板数量一定要涨，但规范一旦破，涨得越多越难看。先立规矩，再扩产。

如果要动拆页：先决定「第二页起要不要重复底图」。这个决定会反过来影响拆页算法（换图要不要重新搜图、要不要等网络）。

06元教训

这次审计最该记住的不是哪个 bug，而是上一轮调研的方法有硬伤：我花了几轮去外部找方案，却没先读一遍自家代码，于是得出「12 套扁平主题」「没有对比度计算」两个错误判断，还基于它们设计了「重构方案」。

正确顺序应该是：先 grep 现状 → 再找外部差距 → 最后才谈借鉴。否则容易把「自家已有的东西」当成「外部先进经验」重新发明一遍，还发明得更差。

另外一点：外部方案的价值是有边界的。它们在「怎么让 AI 写 HTML 出图」这件事上很成熟，但在排版规范上，项目手里的归藏体系是更细的答案。这次我把两者权重搞反了。

还有一条比方法更根本的：用户假设错了，后面全错。我连着两轮用错 —— 先按「大众产品」开新手引导的药，再按「单人工具」砍模板数量。开源项目的正确假设是：作者是第一个用户，但不是唯一用户；拿「我用不着」当砍功能的理由，在这里不成立。

审计方式：源码走查（templates.js / style-system.md / cover-lab.html）+ 纯函数批量实测（13 个标题用例 × 5 个版式）+ WCAG 对比度实算 + 真实渲染截图对比。
数据可复现：断行测试脚本从原型 <script> 中直接抽取函数执行，非重写。
