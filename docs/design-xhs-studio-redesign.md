# 小红书 Studio 重设计方案（2026-10-30）

> 状态：**方案 + 可交互原型，未落地**。按用户要求「先做方案和 html 原型图可交互的，别急着动手」。
> 原型：`docs/prototypes/xhs-studio-redesign.html`
> 本轮不改任何 `pwa/src/` 代码（已核实 git 零改动）。

---

## 0. 一句话结论

**现在的页面把「10 个设置项 + 22 张风格卡」一次摊在用户面前，而用户真正要的只有一件事：把一句话变成一张能发的小红书图。**

重设计的核心不是「重新配色」，而是**把设置项从首屏赶走，把两条路径（标题图 / 长文）分开，把搜图从三级菜单提到一级**。

---

## 1. 现状诊断（代码实证，不是感觉）

| 问题 | 实据 |
|---|---|
| 首屏一次性暴露 10 个设置项 | `pwa/src/cover/index.js` 左栏 7 个 `cv-sec`：文案 / 署名 / 字体 / 文字玩法 / 尺寸 / 底图 / 文字位置 |
| 风格卡 22+ 张同屏 | catalog：GUIZANG 2 + TEMPLATE 10 + LAYOUT 12 |
| **特色功能埋在三层** | 搜图要「左栏第 6 个分区『底图』→ 点开 → 再点『联网搜图』」才见到（`index.js:1176-1181`） |
| 标题图和长文混在一起 | 中栏同时有「保存大图」「整套图文」「标题图结果」「示例成品墙」，用户分不清该点哪个 |
| 三栏断点散乱 | `cover.css` 有 10 个 `@media`，主布局 `320px + 1fr + clamp(492px,34.5vw,520px)` |

**「懵」的根因不是信息太多，而是「没有告诉用户从哪开始」。**

## 2. 第一原理推导

用户原话：「用户是想最快的途径去设计小红书的标题图，或者长文」。

拆成两个任务，二者形态完全不同：

| | 标题图 | 长文图文 |
|---|---|---|
| 输入 | 一句话（标题 + 小字） | 一整篇文章 |
| 主视觉 | **照片**（搜图底图） | **文字**（排版） |
| 成功标准 | 一眼好看、能点进去 | 每页能读、整套统一 |
| 关键能力 | 搜图 + 构图 + 文字保护 | 自动分页 + 版式角色 |
| 页数 | 1 张 | 3–9 张 |

→ **必须分成两条独立路径**，首屏二选一。混在一起是当前所有混乱的源头。

## 3. 双路径信息架构

> ⚠️ **本章 IA 已被 [`design-module-split-ia.md`](design-module-split-ia.md) 取代（2026-10-31 项目所有者拍板）**：
> 「标题图 / 长文图文」不再是封面页内的二级切换，而是拆成**三个平级顶级模块**
> （公众号排版 / 小红书标题图 / 小红书长图文），顶栏三 tab 导航。本章保留作历史；
> 其余章节（§4 搜图、§5 版式、§6 长文模板、§7 数值、§11 可读性口径）继续有效。

### 首屏结构（三级信息，越往下越少人用）

```
┌──────────────────────────────────────────────────┐
│  [ 标题图 ]  [ 长文图文 ]          ← 路径切换，占一行的 1/6
├──────────────────────────────────────────────────┤
│                                                  │
│   ① 一句话（输入框，首屏唯一主角）                │
│      ┌────────────────────────────────────┐      │
│      │ 写个标题，比如「周末去了趟海边」    │      │
│      └────────────────────────────────────┘      │
│                                                  │
│   ② 配图方式（三个并列大按钮，不做成 chip）        │
│      ┌──────────┐ ┌──────────┐ ┌──────────┐     │
│      │ 🔍 搜一张 │ │ ⬆ 传一张 │ │ 🎨 不要图 │     │
│      │  好图     │ │          │ │ 纯文字   │     │
│      └──────────┘ └──────────┘ └──────────┘     │
│                                                  │
│   ③ 预览（实时，不点生成也能看）                  │
│                                                  │
│   [ 保存图片 ]        ⚙ 调整版式/字体/尺寸        │
└──────────────────────────────────────────────────┘
```

### 为什么这样排（每个元素的存在理由）

| 元素 | 为什么必须在这一屏 |
|---|---|
| 路径切换 | 两条路形态完全不同，选错要重来 |
| 输入框 | 唯一的信息入口，用户的全部输入就是一句话 |
| **搜图按钮** | **特色功能，必须显性**。同类软件不一定有，埋起来等于没有 |
| 上传 / 不要图 | 搜不到或不想用图时的退路，不能是死路 |
| 实时预览 | 让用户在点「保存」前就确定好不好看，避免反复试错 |
| 保存 | 唯一的交付动作，主按钮 |
| 「调整」入口 | 高级设置的去处，**但不占首屏视觉重量** |

### 收进「调整」的（渐进披露第二级）

字体 / 文字玩法 / 文字位置 / 磨砂 / 署名 / 尺寸 / 版式细选。

**理由**：这些都不是「从 0 到 1 出图」的必要条件。默认值就能出好看的图，只有想微调的人才需要。按用户使用频率排序，绝大多数人一次都不会点开。

### 收进「更多」的（第三级）

九宫格切图 / 打包整套 / 历史记录。

## 4. 搜图：从设置项升级为特色功能（用户重点要求）

### 现状 vs 目标

| | 现状 | 目标 |
|---|---|---|
| 层级 | 第 6 个分区 → 点开 → 再点子按钮（**3 步**） | 首屏一级，**1 步** |
| 形态 | 藏在「底图」的三个 chip 里 | 与「上传」「不要图」并列的**大按钮**，带图标和说明 |
| 心智 | 「这是底图设置的一个选项」 | 「这是 SuperSu 的特色：一句话帮你找到配图」 |

### 建议的主流程（比现状顺得多）

```
输入「周末去了趟海边」
   ↓
自动从标题提取关键词（复用现有 ZH_EN 词表：海边 → beach ocean）
   ↓
点「搜一张好图」→ 直接出 6 张候选
   ↓
选一张 → 立刻看到「图 + 标题 + 小字」的成品
```

**关键改进：关键词从标题自动提取**。用户不用再单独想搜图关键词，写标题时顺手就搜了。

### 技术事实（已核查，设计时要尊重）

- 纯前端 BYOK，图源仅 **Pexels 一家**（`pwa/src/cover/search.js`），原生支持中文
- 有 `ZH_EN` 词表做中英映射（40+ 常用词：海边/日落/森林/咖啡/猫咪…）
- 结果缓存 24 小时，按 Key 签名隔离
- **必须用户自填免费 Key**

### 没 Key 时的降级（不能报错）

首屏「搜一张好图」按钮常驻可见，但未配 Key 时点击 → 弹出**一句话说明 + 一个直达配置的链接**，文案：

> 搜图需要一次性的免费 Key（Pexels，1 分钟申请），配好后永久可用。
> [去配置] [先用纯色版式]

**不要**：把按钮置灰（用户不知道为什么不亮）、弹错误 toast（像出故障）。

### 搜图无结果时

不进入死路，降级到「纯色版式 + 大字」，并给一句 `没搜到合适的图，先用纯色版式试试`。

## 5. 备选版式（「图 + 标题 + 小字」与「纯文字」两条子路）

用户原话：「搜图出来的图片+标题+小字，适合」。

**核心矛盾**：文字要看得清，但照片不能被压成灰雾（之前踩过这个坑）。
**解法**：不靠压暗救可读性，而是**让文字和照片在空间上分开**，只在必须重叠时用局部 scrim。

### 12 种版式总览（2026-10-31 定案）

原型从「六种构图」扩成 **12 种版式，分两组**。原因：真系统原本已有 8 种封面版式
（归藏 magazine/swiss/bigtype + layouts 的 image-led/quote/number/list）和 7 种标题排法，
早期原型只画了 6 种构图，等于把已有能力丢了。现在按「有没有图」分成两组，原能力零丢失：

| 组 | 版式 | 数量 | 来源 |
|---|---|---|---|
| ① **图文封面**（有底图） | C1 刊头 / C2 全出血 / C3 左文右图 / C4 上下分栏 / C5 卡片浮层 / C6 安静区 | 6 | 本轮新设计；C2 即真系统的 `image-led` |
| ② **纯文字封面**（不用底图） | T1 杂志刊头 / T2 瑞士极简 / T3 大字报 / T4 金句 / T5 编号大字 / T6 清单 | 6 | 真系统既有：归藏 magazine / swiss / bigtype + layouts 的 quote / number / list |

**为什么分两组**：用户第一步要决定的是「有没有图」，第二步才是排版。
混在一个网格里会让 12 个平级选项互相抢注意力（§3 的核心是渐进披露）。

### ① 图文封面六种构图

| # | 构图 | 结构 | 适用 | 文字保护方式 |
|---|---|---|---|---|
| **C1** | **刊头照片带** | 图占顶部 36%（520px），文字在下方纸面 | 通用首选，最稳 | **不需要压暗**——图与字根本不重叠，只在交界处一条 accent 细线 |
| **C2** | 全出血压字 | 图铺满，文字压底部 | 氛围强、图很干净时 | 局部 scrim 只压文字带（底部 45%），4 档渐变防色带，**α 按实测亮度反解、封顶 0.30**（见 §11；旧的「峰值 0.24–0.40」口径已作废——0.40 那档压完就是灰雾） |
| **C3** | 左文右图 | 竖向 55/45 分栏，图在右 | 竖构图照片（人像、单品） | 天然不重叠；文字侧纯色纸面 |
| **C4** | 上下分栏 | 上图下字，50/50 | 图是主体、标题短 | 交界处 8px 柔和过渡即可 |
| **C5** | 卡片浮层 | 图铺满 + 白色圆角卡片承载文字 | 需要"高级感"、图文分离清晰 | 卡片本身即保护，不需要 scrim |
| **C6** | 落进安静区 | 图铺满，文字落在实测最安静的带 | 图有大片留白（天空、墙面） | 复用 `analyze.js` 的 WCAG 分带实测，只在最亮处不达标时补 ≤0.30 |

### ② 纯文字封面六种（不用底图）

**这一组存在的理由**：搜不到合适的图时，封面不能就废了。
它们靠留白 + 字号对比 + 少量色块撑住画面，出图也最快（不用等图片解码）。

| # | 版式 | 结构 | 适用 | 真系统对应 |
|---|---|---|---|---|
| **T1** | 杂志刊头 | Vol. 期号 + 大标题 + 色条 + 引言，**贴底**排版 | 长文、随笔、有栏目感的内容 | `templates.js` 归藏 Editorial |
| **T2** | 瑞士极简 | 白纸 + 细体大字（weight 300）+ 克莱因蓝强调，左对齐 | 观点、清单、理性表达 | 归藏 Swiss |
| **T3** | 大字报 | 垂直居中 + 强调色块压题，字号最大 | 金句、强观点、标题短 | 归藏 Bigtype |
| **T4** | 金句 | 居中大引号 + 标题 + 短色条 + 署名 | 一句打动人的话 | `layouts.js` buildQuote |
| **T5** | 编号大字 | 超大数字当主视觉（从标题提取，没有就取月号） | 盘点、系列第 N 期 | `layouts.js` buildNumber |
| **T6** | 清单 | 标题 + 编号条目行，细线分隔 | 干货清单、要点总结 | `layouts.js` buildList |

**交互配套**：选中任意 T 版式时，左侧「配图来源 / 搜图」整块自动收起
（`#secImg.muted-by-layout`）——不用图就不该再让用户搜图，否则自相矛盾。

### 标题排法（3 档）与字体（4 档）

真系统 `textmode.js` 原有 7 种标题玩法，**按用户拍板只保留 2 种**，其余
（offset 错位 / rainbow 逐字变色 / outline 描边 / stagger 错行）**不要**：

| # | 排法 | 效果 | 实现 |
|---|---|---|---|
| 1 | **默认** | 沿用版式原本的标题排法 | 不加类 |
| 2 | **大字压阵** | 字号撑到极限、`line-height:.98`、`font-weight:900` | `.tm-poster` |
| 3 | **竖排** | `writing-mode:vertical-rl` + `text-orientation:upright` | `.tm-vertical` |

⚠️ **竖排必须给 `max-height` 约束**（78%）并从右侧展开，否则长标题会一路顶出画布
—— 真系统实测踩过这个坑。原型已实测 T1/C2 两种版式的竖排都在卡内。

字体 4 档（对齐 `textmode.js` 的 `TEXT_FONTS`）：思源宋体 / 思源黑体 / 得意黑 / 跟随色板。

**这两项对两组版式都生效**（`fontTmodeCls()` 共用），不是只有图文封面能用。

### 文字保护三条铁律（踩坑总结）

1. **不要整图压暗** —— 照片会变灰雾，等于白放一张图（浅色图最明显，实测过）
2. **scrim 只盖文字，不盖图** —— 这是 Material 局部 scrim 的本意；只压文字所在的那一条
3. **投影是辅助，不是主力** —— scrim 管 90% 场景；投影只补边缘，且只给压在照片上的字用（纸面正文加投影会让笔画发虚）

### 「标题 + 小字」的字号关系

| 角色 | 字号（1080 宽） | 字重 | 手机等效（375 屏） |
|---|---|---|---|
| 主标题 | 96–128px | 500（衬线）/ 300（瑞士无衬线） | 33–44px |
| 小字 / 副标 | **36px** | 400 | 12.5px |
| 页脚 metadata | 19–20px | mono 500 | 6.6–7px |

**比例约 3:1**（标题 : 小字），这是小红书的通行比例——差距不够大就没有层级感。
⚠️ 小字不能压到 30–34px：375 屏上只有 10.4–11.8px，比微信正文（16–17px）小太多，用户会反馈「看不清」。36px 是实测下限（见 §11.4）。

⚠️ 大标题**必须 weight 200–500**（`style-system.md` 硬规则：the larger, the lighter）。700+ 会退化成"信息图横幅"。

## 6. 长文版式：以文字为主，但要更好看

### 6.0 长图文 = 封面 + 内页（2026-10-31 按行业标准重构）

> ⚠️ **本节曾走错过一次，先记教训**：上一版把标题图的 12 套视觉模板直接套到长文每一页上。
> 错的。长图文有它自己的形态，**和标题图没有关系**。
> 用户原话：「长图长文这个不一定要和标题图的 12 套一样啊，我是让你去调研人家的长图文怎么生成、
> 什么格式，和标题没关系，至于背景图那是搜图模块增加的功能，和版式不同啊！」

**行业标准**（真系统 `pwa/src/cover/story.js` 的注释里记着它的调研：红墨 / 创客贴 / 火兔 / A9）：

> 「输入主题 → 封面 + 3~6 张内页，一次出齐，整套风格统一」，单独出一张封面反而是少数派。

照抄它的四条原则：

1. **复用现有版式骨架**，不新写一套排版
2. **内容从正文自动拆页**，不要求用户手工分页
3. **一套图共用同一色板**；封面可铺底图，**内页不铺底图**（竞品的内页都是纯色排版，铺图反而乱）
4. 一次只出 3:4（多尺寸会让页数翻倍、用户懵）

#### 6.0.1 长文只有一个维度：**一套模板**

> ⚠️ **第二次返工的结论**：上一版把它拆成「封面版式 + 内页风格」两个选择器，也是错的。
> 用户原话：「假如是长图长文的第一页和其他页完全不同，也很奇怪啊。
> 你不能搜索一下其他人是怎么做的吗？不要自己研究啊。」

**竞品实证**（详见 `docs/research-2026-10-31-xhs-longform-generators.md`）：

| 证据 | 说明 |
|---|---|
| XHS-TextCard 编辑器 | 「模板与设置」三 Tab：**内页**（模板 12 选 1、比例、背景图、排版、字体、配色）／**封面**（启用开关、封面图片、封面字号、社交图标——**没有版式选择**）／导出 |
| XHS-TextCard API | 只有一个 `template` 字段，**不是每页一个** |
| CreatorFlow | 「Same color palette across all slides」「Repeated design elements」 |
| Dhia Portfolio | 「**One template family, not fifty one-offs**」 |

**结论**：模板是**整套**图文的风格，封面只是这套模板的第 1 页。
封面能调的只有「有没有底图、用哪张」，不是「换成另一种版式」。

| 维度 | 决定什么 | 作用域 |
|---|---|---|
| **模板**（12 套） | 整套图文的视觉风格（配色、页眉页脚、装饰、字号气质） | 封面 + 全部内页 |
| **页面角色**（6 种） | 这一页装什么内容、用什么结构 | 由内容自动判定 |

#### 6.0.2 页数上限与截断策略

`STORY_MAX_PAGES = 6`（封面 + 最多 5 张内页）。超限时：

1. **先合并**：把相邻两个 dense 页合成一页，按实测高度验算装得下才合
2. **合并不下才截断**，并在返回值上带 `truncated` 字数，自检条明确提示

不允许静默丢内容，也不允许靠加装饰填空（§6 原文口径）。

#### 6.0.3 12 套视觉模板（**整套**图文共用）

模板来源与版权说明见 `THIRD_PARTY_NOTICES.md` §3（XHS-TextCard，MIT，**仅借鉴视觉、代码独立重写**）。

#### ✅ 落地状态（2026-10-31，原型已改 + 1080 真宽实测）

分页器 `buildLong()` 现在按上表实现，但补了两类**上表没覆盖**的约束 —— 都是实测出来的：

**① 欠填的另一面是溢出（会裁掉用户内容，比欠填严重）**

上表只有下限，没有上限。实测 1080 真宽后发现三个角色都会把内容挤出 1124px 的可用高：

| 角色 | 实测容量 | 落地常量 |
|---|---|---|
| 开篇 | 110 字 91.5% / 140 字 99.6% / **170 字 101.7% 溢出** / 200 字 109.7% | 首段 >120 字就不做开篇页，交给 dense |
| 金句 | 金句30+上下文80 = 94.4% / **+120 = 106.3% 溢出** | 金句+上下文总字数 ≤120 |
| 结尾 | 1 段 150 字 98.3% / **170 字 102.3% 溢出**；**2 段 156 字 104.2%**；**3 段 140 字 100.2%** | `closingCap(n) = max(100, 150 − 10×(n−1))` |

**② dense 的填充率不只取决于总字数，还取决于段数**

同样 160 字：2 段×80 = 86.4% 安全，4 段×40 = **110.2% 溢出**（每段多一次 `--pgap` + 半行浪费）。
原装箱只看 `字数 < 170`，每段 60 字时会装进 3 段共 180 字 = **106.4% 溢出**。
现改为预估行数包络：**`Σ ceil(字数/17) + 段数 ≤ 13`**，与 6 个实测点全部吻合
（190 字 1 段 / 2×80 / 3×50 / 4×30 安全；2×120 / 3×60 / 4×40 溢出）。

**③ 一个不能修的边界：dense 单段 120–139 字恒为 66.5%**

8 行 = 767px，767/1124 = 68.2%（理论），实测 66.5%（段落 margin 与行盒取整）；
要够 68% 必须 9 行（≥140 字），而第二段一加就是 16 行 → 134.7% 溢出。
**这与上面对开篇/金句的裁定同源——「大字版式占高少是大字的代价，不是排版失误」。接受，不靠加装饰填空。**
已写成 `DENSE_SINGLE_SEG_FLOOR = 66.5` 常量注释，避免下一个人重复调查。

**④ 结尾页的 guard**：原逻辑无条件把 dense 末段摘出去做 closing，
导致上一页掉到 66.5%（310 字样例：121+36 字本可一页装下，摘后只剩 121 字）。
现摘段前先验算 `rest >= DENSE_MIN_FILL_CHARS (140)`，不达标就整页留着。

## 11. 底图文字可读性：判定口径（2026-10-30 拍板）

### 11.1 目标对比度：4.5:1（取严，不按字号分级）

视觉侧曾出现两个口径分歧：「L>0.40 才救不回来」vs「L≈0.26 就该封顶 α 0.30」。
**拍板取后者（4.5:1）**，理由：

1. 用户明确抱怨过「文字和底图区分不开」，可读性优先于照片保真
2. 卡片上**标题与小字在同一文字带**，不能只保标题的 3:1 而牺牲小字的 4.5:1
3. 按 4.5 压完变灰板 = 这张图本来就不适合该构图，应换图或换构图（判定逻辑会提示「改用 C1/C5」）

**落地口径（写死，不再讨论）：**
- 文字带内最小对比度目标 **4.5:1**，不区分大标题/小字
- scrim alpha 由 **sRGB 空间反解** `α = (sMax − invLin(0.1833)) / max(1, sMax − SCRIM_SRGB)`，**封顶 0.30**
  （`sMax = invLin(max)`，`SCRIM_SRGB = 10` —— 与卡片 CSS 的 `rgba(10,9,8,α)` 一致。分母不能简化成 `sMax`：那等于假设 scrim 是纯黑，会把 α 算小 0.009，压不够。）
  （⚠️ 2026-10-30 二次修正：原先写的 `1 − 0.1833/max` 是按**线性亮度**合成推的，实测证明错的——见 §11.8。两套公式算出的 α 差 1.6–2.1 倍，旧式会把照片多压一倍。）
- 达不到 → 判不合格 + 提示换构图，**不做「压到 0.4 凑合」**
- scrim 的几何范围（top/height）必须由同一个 zone 变量驱动，保证「面板写只盖 38%」时画出来真是 38%

### 11.2 四种判定（每张图自己算，无魔法数字）

```
zone = 由「文字块实际高度」反推，不是常量（见 §11.10）
busy = 带内最大标准差 > 0.15      ← 明暗交错，任何单色字都会在某处失效

① 不 busy 且白字 ≥4.5  → 白字，α=0（不压暗）
② 不 busy 且黑字 ≥4.5  → 黑字，α=0
③ 不 busy 且 α(sRGB) = (invLin(max) − invLin(0.1833)) / invLin(max) ≤ 0.30 → 白字 + 该 α
④ 其余 → 判不合格，α 封顶 0.30，提示「建议改用 C1 / C5」
```

实测数据（无头 Chrome + canvas 逐像素算 sRGB 相对亮度，10 带 mean + 带内 sd）。
下表按 **C2 + 7 字标题 108px + 13 字小字 36px** 的真实文字带（71.2–86.8%）计算：

| 照片 | 文字带实测 L | 判定 | 结论 |
|---|---|---|---|
| 海边雾晨 | 0.039–0.045 | 白字 11.1:1 | 免压暗 |
| 夜街路灯 | 0.014–0.021 | 白字 14.8:1 | 免压暗 |
| 山野秋千 | 0.136–0.197 | 白字 4.5:1 | **α 0.03**（旧算法要 0.20） |
| 浅色纸浪 | 0.106–0.249 | 白字 4.5:1 | **α 0.13**（旧算法误判为不合格） |
| 旧照片堆 | 0.140–0.260，sd 0.22 | 3.4:1 | **不合格**：原因是 busy，不是 α |

**两个修正叠加后的结论：5 张里有 2 张完全免压暗，2 张只需 α ≤0.13，只有 1 张真不可用。**
之前的旧算法（线性公式 + 常量 62% 带）把 3 张判重了、1 张判错了。

**重要发现：多数照片的 C2 其实零压暗。** 之前「下半部像泡过墨」是把 α 写死 0.38 造成的，不是照片的问题。

### 11.3 accent 双 token（8 套色板里 4 套过不了文字对比度）

| 色板 | accent 原值 | 当文字用 | 修法 |
|---|---|---|---|
| 柠檬黄 | `#C5E803` | **1.35:1**（基本看不见） | `--accentText: #4F5A00`（7.19:1） |
| 安全橙 | `#FF6B35` | **2.71:1** | `--accentText: #A6390A`（6.26:1） |
| 沙丘暖纸 | `#8f7650` | **3.48:1** | `--accentText: #6b5334`（5.82:1） |
| 牛皮纸 | `#9b5a2e` | **4.11:1** | `--accentText: #7c4520`（5.87:1） |
| 应用外壳次要文字 | `#8a8378` | 3.59:1 | `#6d6656`（5.46:1） |

**结论：`--accent`（填色/细线）与 `--accentText`（文字）必须拆两个 token。**
这不是调色问题，是 token 建模问题——同一个颜色「当色块」和「当字」是两个不同角色。

### 11.4 标题与小字的比例

原 108:32 = 3.4:1 → 375 屏上小字只有 11.1px。

### 11.8 修正：scrim 的混色发生在 sRGB 空间，不是线性空间

**这条推翻了 §11.1 原来的反解公式，必须看。**

浏览器合成 `rgba(0,0,0,α)` 时是在 **gamma 编码的 sRGB 数值上**做加权，不是在相对亮度上。所以正确的模型是：

```
s' = s × (1 − α)          s 是 sRGB 编码值（0–1）
L' = lin(s')              L' 才是相对亮度
```

而不是 `L' = L × (1 − α)`。

**实测验证**（canvas 合成 → 读回像素，4 档亮度 × 4 档 α）：

| 源亮度 L | α | 实测 L' | 线性模型 | sRGB 模型 |
|---|---|---|---|---|
| 0.223 | 0.20 | **0.1384** | 0.1784 | 0.1383 |
| 0.350 | 0.30 | **0.1590** | 0.2450 | 0.1613 |
| 0.509 | 0.30 | **0.2307** | 0.3563 | 0.2319 |
| 0.733 | 0.38 | **0.2502** | 0.4545 | 0.2536 |

实测与 sRGB 模型误差 ≤0.002，与线性模型误差最大 0.2 —— **线性模型彻底不成立**。

> **⚠️ 补注（2026-10-31，代码复算后加的）**：上表的「≤0.002」是按**纯黑 scrim**
> （`scrimSrgb = 0`，即 `rgba(0,0,0,α)`）算的 —— 实测 canvas 当时画的就是纯黑。
> 用代码逐格反推最贴合的底色，四格全部落在 `scrimSrgb ≈ 0`（误差 0.0001–0.0034）。
> 换成卡片实际底色 `10` 后误差变成 0.006–0.019，`12` 则是 0.007–0.022。
> **这不影响结论**（sRGB 0.0034 vs 线性 0.2043，差 60 倍），但看数字时要知道基准是哪一种：
> 上表验证的是「sRGB 空间 vs 线性空间」这个**模型选择**，不是某个具体底色的精度。

**两套公式算出的 α 差多少：**

| 源亮度 L | 达 4.5:1 需要 α（sRGB） | 旧式（线性） | 倍数 |
|---|---|---|---|
| 0.20 | 0.04 | 0.08 | 2.10× |
| 0.26 | 0.15 | 0.30 | 1.98× |
| 0.35 | 0.26 | 0.48 | 1.85× |
| 0.50 | 0.37 | 0.63 | 1.72× |
| 0.90 | 0.51 | 0.80 | 1.55× |

**后果**：用旧式，山野秋千会被算成 α 0.20，实际只需 0.10 —— **照片被多压了一倍**，正是用户抱怨的「压成灰雾」。这不只是数值精度问题，是把「不压暗」这条设计原则抵消掉的一半。

**结论（落地口径）**：

1. α 一律用 sRGB 反解，`MAX_ALPHA = 0.30` 这条**不变**（它是「压过这条就不叫压暗、叫盖灰」的感知判断，与公式无关）。
2. 换公式后 **不合格的门槛后移了**：正确的临界点是 **L≈0.377**（`scrimSrgb=10`；用 analyze.js 的 12 则是 0.373，纯黑假设是 0.399）。
   ⚠️ 本文件早先写过的「L≈0.51」是我算错的，已作废 —— 0.51 处 α 已经 0.394，远在 0.30 之上。这个错值得记下来：**同一个数我在两轮里给出了 0.26 / 0.51 两个错值，都是凭手算推的，没跑二分**。凡是「某个阈值等于多少」的结论，一律用代码解，不手推。
3. **真正拦住烂照片的是 `busy`（带内 sd>0.15），不是 α 数学。** 旧照片堆（sd 0.25）按新公式只需 α 0.15，但依然判不合格——判定逻辑里 `busy` 必须排在 α 之前，否则会放过它。
4. ~~原型当前实现仍是旧式（线性），**已列入待修**：等文件交回后替换为 `alphaFor()`，并重拍 C2/C6 截图对比。~~

### 11.10 文字带必须由「文字块」反推（常量 62% 是错的）

原实现把 C2 的 zone 写死 `[62,100]`、C6 `[60,98]`。**这是错的**，因为文字块高度随标题行数变化：

| 标题 | 字号 | 行数 | 文字带起点 | 与常量 62% 的差 |
|---|---|---|---|---|
| 「周末去了趟海边」7 字 | 108px（全宽 904，每行 8 字） | 1 行 | 79.0% | 高估 17 个点（过度压暗） |
| 16 字 | 92px | 2 行 | 79.0% | 同上 |
| 24 字 | 92px | 3 行 | **63.4%** | 恰好贴边，稍有增字就漏测 |

正确做法：

```
行数   = ceil(字数 / floor(可用宽 / 字号))
块高   = 行数 × 字号 × 1.22 + 小字行数 × 36 × 1.62 + 间距
zone_y0 = (卡片高 − 底部偏移 − 块高) / 卡片高
```

**两个后果都要记住**：

1. 短标题时 zone 上移到 79% → 用的是照片最底部那块，**往往更暗、更干净**，压暗需求直接归零（海边雾晨 11.1:1）。
2. 长标题时 zone 上移到 63% → 会跨进照片的亮部，可能从「免压暗」翻成「需 scrim」或「不合格」。**同一张照片、同一个构图，标题变长就会变不合格** —— 这是真实行为，不是 bug。

**✅ 落地状态（2026-10-31）**：常量 `ZONES` 已删除，改为 `ZONE_ANCHOR`（只记锚定方式：
`c2: {bottomOff:190}` / `c6: {topOff:906}`）+ `zoneOf(comp, title, sub, ttlSize)` 由实际文字块反推。
调用点、`verdictOf()` 签名、scrim 的 `top/height` 全部改成吃同一个 zone —— 面板文案与实际画的区域由同一份几何算出，
不会再出现「面板写只盖 38%、实际画 45%」。

配套实现：`docs/prototypes/xhs-layout-fit.js`（纯函数，无 DOM，可单测）
- `alphaFor(L)` —— sRGB 空间反解 α
- `zoneFromBlock({...})` —— 由文字块反推带
- `judgeZone(bands, sds, zone)` —— 四种判定，busy 优先
- `fitTitle(text, width, base, wantLines)` —— 按字数反算字号
- `subWrap(text, width, size)` —— 小字孤字检测
- `maxParaChars()` → 单段上限 **190 字**（204 理论值 − 余量）
- `fillVerdict(role, fill, anchors)` —— §6 分档断言

### 11.11 与 `pwa/src/cover/analyze.js` 对齐（含一处必须覆盖的钳制）

**结论先写**：`analyze.js` 的数学是对的，必须在 Phase 3 复用；但它的 **α 钳制区间 `[0.24, 0.62]` 与本项目口径冲突，必须覆盖成 `[0, 0.30]`**。

#### 一致的部分（逐点验证过）

`docs/prototypes/xhs-layout-fit.js` 里的 `scrimmedLum / relLum / contrast` 与 `analyze.js` **数值完全一致**（27 个 L × α × scrimSrgb 组合，最大偏差 `0.00e+0`）：

```js
// analyze.js:44
export function scrimmedLum(L, alpha, scrimSrgb = 12) {
  if (alpha <= 0) return L;
  const s = invLin(L);                       // 0–255
  const out = s * (1 - alpha) + scrimSrgb * alpha;
  return toLin(out);
}
```

`analyze.js` 的注释（第 42 行）自己就写了这条铁律：**「必须在 sRGB 空间混合再算亮度 —— 直接 L×(1-a) 会严重高估效果」**。我上一轮自己推的线性公式，正是它警告过的错。

#### 冲突的部分：`analyze.js:165` 的钳制

```js
let a = (sMax - targetS) / Math.max(1, sMax - 12);
a = Math.min(0.62, Math.max(0.24, a));   // ← 问题在这
```

实测这个区间两侧都会出问题：

| 底亮度 L | 真实需要 α | 钳制后 α | 后果 |
|---|---|---|---|
| 0.20 | 0.045 | **0.24** | 多压 5 倍，照片无故变暗（6.2:1，本可 5 倍亮） |
| 0.30 | 0.22 | **0.24** | 轻微过度（4.7:1） |
| 0.51 | 0.40 | 0.40 | **超过 0.30**，成品偏灰 |
| 0.90 | 0.54 | 0.54 | **严重灰雾**，正是用户抱怨的那件事 |

更矛盾的是：**`analyze.js` 自己的文件头注释写的是「峰值 ≤0.30」**（第 13 行），代码却允许到 0.62。文档与实现两张皮，就在同一个文件里。

#### 落地口径

```js
import { scrimmedLum, relLum, contrastRatio } from './analyze.js';

// 复用它的数学，但策略由本设计定
const a = alphaFor(maxL, 10);            // 不钳制
if (a <= 0.30) applyScrim(a);            // 0–0.30：压
else reject('改用 C1 / C5');              // >0.30：不压，换构图
```

三条硬约束：

1. **`SCRIM_SRGB = 10`**，与卡片 CSS 的 `rgba(10,9,8,α)` 一致。（`analyze.js` 用 12 是因为它那套底色是 `rgba(12,11,10)`。两者差 <0.001，可忽略，但**同一个文件里只能有一个值**。）
2. **不要 0.24 下限**：需要 0.04 就只压 0.04。「压一点点看起来更像设计」不是理由，用户要的是照片清楚。
3. **不要 0.62 上限**：超过 0.30 就不是压暗，是把照片盖成灰板；此时正确动作是换构图，不是加大 α。

#### Phase 3 硬约束（比公式更重要）

> **必须 `import { scrimmedLum, contrastRatio, relLum } from './analyze.js'`，不要在 cards.js / story.js 里复制一份数学。**
> 两套数学并存一定漂移，而漂移的表现是「面板显示 4.5:1 ✓ 但画面上字看不清」——这类 bug 极难查，因为它只在部分照片上出现。

原型侧的镜像实现（`xhs-layout-fit.js`）只用于 node 单测与原型演示，它的一致性由逐点 parity 保证；**Phase 3 不要引用它，要引用 `analyze.js`**。

- **交互**：色板控件整行置灰 + `aria-disabled="true"`，旁边出现一行提示：**「这套模板自带配色 · 色板不参与」**；切回 3 套跟随模板时恢复可点、提示消失。不弹 toast。
- **预览头部**：色板名称行（V5 已修的那处）同步显示为「暗夜深思 · 自带配色」这类形式。
- **读屏**：提示文案容器 `role="status" aria-live="polite"`。
- **不改数据**：`LONG_TPLS[].palette` 字段语义不动（null = 跟随），这只是 UI 层提示。
- **验收**：9 套锁色模板逐套 → 色板置灰 + 提示可见；3 套跟随 → 可点、提示消失；锁色状态下切换色板不改变渲染（防「点了没反应」误解为坏掉——点了本来就不该有反应，提示必须在场）。

### 12.2 决策 2-① · 内页背景图

- **入口**：长文右栏「尺寸」之后新增一组「内页背景图」，默认关。开启后上传一张图；若封面已配底图，给一个「复用封面那张」的快捷项（少一次上传，且两图同源更整）。
- **渲染**：图片 `object-fit:cover` 铺满**所有内页**（封面不受影响——封面底图是另一个维度 `state.img`），上面叠**当前模板纸色的 85% 蒙层**，再往上是模板装饰与正文。z 序：底图 → 纸色蒙层 → 模板装饰 → 文字。
- **为什么用高蒙层，不抄竞品的「原样铺满」**：内页是 52px 大面积正文，没法像封面那样只对文字带做局部 scrim（全页 scrim = 灰雾，§5 铁律 1 踩过的坑）；竞品「不参与压暗判定」等于把可读性交给运气，我们不抄这一点。85% 蒙层下正文对比度仍按纸色基准计算；落地后用 12 套模板 × 3 张实拍图各验一轮，如果高对比纹理仍干扰，蒙层下限提到 88%。
- **适用范围**：6 套可用（editorial / swiss / notion / book / memo / blank）；6 套禁用（polaroid / aura / night / doc / film / starry——照片框、光晕、深色渐变、网格底、遮幅、星空都是自带完整背景体系，铺图会毁掉模板语义），禁用时控件置灰 + 提示「这套模板自带背景」。
- **状态**：`state.longBg`（null | dataURL）。若做持久化，必须走 `supersu.` 前缀并**同步加进 `clearAll()`**（2026-10-30 存储键漏清的教训）。
- **验收**：开启后 6 套可用模板内页均见蒙层图、正文对比度断言不变；6 套禁用模板控件置灰；关闭后完全恢复纯色；导出 PNG 含背景层。

### 12.3 决策 2-② · 强制分页符

- **语义（仅长文 buildLong 管线）**：独占一行的 `---`（允许前后空白）= 强制分页，不再渲染为分隔线。**公众号排版路径的 `---` 语义不变**（那是 format_engine 管线）——两条管线独立，不要以后「顺手统一」。竞品即此语义（XHS-TextCard 文档）。
- **边界规则**：
  1. 连续两个 `---` 只分一次，不产生空页；分页符导致的空页一律丢弃
  2. 文章开头 / 结尾的 `---` 忽略
  3. 手动分页**优先于**自动分页：先按 `---` 切大段，段内再走既有自动分页；总页数仍受 `STORY_MAX_PAGES = 6` 约束，超限走既有「先合并再截断」，自检条提示需包含「手动分页符 X 处」
  4. 分页符打断后的页面角色重新判定，但 `opening` / `closing` 仍只授予自然首页 / 末页（手动分页后的短页按 dense 排，不当开篇）
- **验收**：`---` 分页生效；上述 4 条边界各一例；72 组模板 × 文本回归不破。

### 12.4 决策 2-③ · 水印 / 签名栏

- **入口**：长文右栏新增「签名」输入，默认空 = 关；填了即全内页显示。
- **渲染**：内页页脚区追加 `@签名` 小字，**沿用该模板页脚既有的文字色、字号与位置**，不新造颜色不新增布局。封面页不显示（封面署名走标题体系）。
- **对比度**：页脚色对比度已由模板锁定配色或 accentText 体系保证；落地时 12 套逐套跑对比度断言，个别不达标的模板回退用 `palette.ink`。
- **验收**：填入后每张内页页脚有签名；12 套逐套对比度 ≥4.5:1；清空后完全消失；导出包含。

### 12.5 决策 2-④ · 页码开关

- **入口**：长文右栏「签名」旁加开关「显示页码」，**默认开**（保持现状心智，避免老用户发现页码「丢了」）。
- **范围**：只管各模板 `foot()` 里的页码文本（`2 / 5` 这类）；`closing` 角色的超大装饰数字、页眉元素**不受影响**（那是视觉装饰，不是页码）。
- **实现**：全局布尔，`foot()` 渲染时按开关省略页码 span；位置仍跟随各模板既有布局（editorial 右下 / swiss 左上等），不新增布局。
- **验收**：默认开（现状回归零变化）；关闭后 12 套逐套页码消失、页脚其余元素不动；导出同步。

### 12.6 决策 3 · V6 裁定：不改

**决定：保持现状**（`#save` 在左栏，Tab 序早于构图组），`ux-spec` C18 口径已相应调整。

理由：

1. 本产品移动优先，桌面键盘用户占比极低；roving tabindex 已把 6 个构图按钮收成 **1 个 Tab 站**——保存之后 1 站 + 方向键即换构图，实际成本 2 个键
2. 任何修法都要把 `#save` 移出 `.left` 滚动容器并重排 `.wrap` 的 grid 结构，会波及 375 / 900 / 1180 三档断点 + `.mbar` 底栏 + sheet 的既有实测布局；回归面远大于收益
3. `ux-spec` §5.1 早已记录过「可接受」的判断，本次正式裁定，不再反复
