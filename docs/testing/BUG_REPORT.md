## BUG-01（P0）「清除本地数据」漏删 13 个键，含 API Key

### 对应测试用例
`TC-DATA-06`（清干净）、`TC-DATA-07`（清除后 Key 输入框为空）

### 问题描述
「⋯ → 清除本地数据」的确认框写的是「清除本机保存的草稿、收藏与风格偏好？
文章内容不会上传，删了就找不回」，给了用户「已彻底清空」的预期。
实际只删了 5 个键，**13 个键原样保留**，其中包含：

- `supersu.ai` —— **用户的 LLM API Key 明文**
- `supersu.ai.verified` —— 「测试连接通过」标记（导致 AI 入口在清除后**仍然开着**）
- `supersu.cover.stock.v1` —— **Pexels API Key 明文**
- `supersu.pwa.custom` / `blocks` / `layout` —— 自定义配色与排版覆盖
- `supersu.cover.prefs.v1` / `search.v1` —— 封面偏好与搜图缓存
- `supersu.pwa.seenVersion` 等 6 个更新诊断键

### 复现步骤
1. 打开页面，在 AI 面板填入 API Key 并点「测试连接」通过（或直接执行下面脚本第 1 步）
2. 「⋯」→「清除本地数据」→ 确认
3. 刷新页面
4. 打开 AI 面板，或执行 `Object.keys(localStorage)`

### 预期结果
1. 所有 `supersu.*` 键被清空
2. 刷新后 AI 入口收起（`body.ai-ready` 不存在）
3. AI 面板的 API Key 输入框为空，图库状态显示「未配置」

### 实际结果
```
清除前 10 个键 → 清除后仍剩 8 个
残留敏感数据：supersu.cover.stock.v1 = {"pexels":"QA-PEXELS"}
              supersu.ai = {..., "key":"sk-REAL-LOOKING-KEY-..."}
刷新后 body.ai-ready = true   （AI 入口仍然启用）
AI 面板：Key 框='sk-REAL-LOOKING-' / Pexels 框='PEXELS-SECRET-KE'
         图库状态='已配置：Pexels ✓'
```

### 严重程度
**P0**。理由：这是隐私承诺与实际行为的直接冲突。用户在共享电脑上「清除本地数据」后，
API Key 仍然留在浏览器里，任何后续使用者打开该页面都能在 AI 面板里看到并复制。
且产品文案明确宣称会清空，属于**误导性承诺**。

### 证据
- `output/qa-deep/deep.json` —— 逐键快照（清除前 10 键 / 清除后 8 键 / 残留敏感键）
- `output/qa-round2/report.json` —— R1 / R2 / R2b / R2c 四条独立证据
- `output/qa-independent/report.json` —— E2E-19（本地与线上两次都复现）
- `output/qa-independent/10-clear-all.png` —— 清除后截图

### 初步原因（已定位到代码）
`pwa/src/app.js:1501-1511`：

```js
async function clearAll() {
  if (!confirm('清除本机保存的草稿、收藏与风格偏好？...')) return;
  lsDel(LS.draft); lsDel(LS.fav); lsDel(LS.recent); lsDel(LS.theme); lsDel(LS.mode);
  // ← 只删这 5 个
  try { /* 删 Cache Storage */ } catch {}
  toast('本地数据已清除，刷新后回到初始状态');
}
```

而 `app.js:13-21` 的 `LS` 对象本身就定义了 7 个键，`clearAll` 只用了其中 5 个
（漏了 `LS.blocks`、`LS.layout`）；此外 `LS_CUSTOM`（`app.js:245`）、
`STOCK_KEY`（`app.js:939`）、`ai.js` 的 `LS_AI`/`LS_VERIFIED`、
`cover/index.js` 的 `PREFS`、`cover/search.js` 的 `CACHE_KEY`、
`update/index.js` 的 6 个键，全都没被删。

**根因是「存储键分散在 5 个模块、没有统一注册表」**——`clearAll` 是按当时记得的键手写的，
后续模块加键时没人回头补。这类缺陷会随功能增长持续恶化。

### 建议修复方向
1. **首选：建立单一存储键注册表**。新增 `pwa/src/storage.js` 导出 `ALL_KEYS`（或让各模块
   把自己的键注册进来），`clearAll` 遍历 `Object.keys(localStorage).filter(k => k.startsWith('supersu.'))`
   统一删除。用前缀匹配比维护清单更不容易漏。
2. 删除后**立刻验证**：`clearAll` 末尾断言 `localStorage` 里已无 `supersu.` 前缀键，
   有残留就 `console.warn`（让下一个漏删的键自己暴露出来）。
3. 确认框文案改成与行为一致（如「清除草稿、偏好、以及你填过的 API Key」），
   或提供「只清草稿 / 全部清除」两档。
4. 修完补一条门禁用例：清除后断言 `Object.keys(localStorage).filter(k=>k.startsWith('supersu.')).length === 0`。

### 可能影响的其他功能
- **AI 入口门控**：`ai-ready` 依赖 `supersu.ai.verified`，不清除 → 清除后 AI 仍启用（已实测）。
- **图库搜图**：Pexels Key 残留 → 清除后仍能搜图，用户以为已重置。
- **主题/版式**：`blocks`/`layout`/`custom` 残留 → 清除后用户改过的版式与配色仍生效，
  与「刷新后回到初始状态」的提示不符。

### 回归用例
`TC-DATA-06`、`TC-DATA-07`（修完必须两条都过）

## BUG-02（P3）图库 Key 教程文案与实际图源不符

### 对应测试用例
`TC-DOC-03`

### 问题描述
「AI 面板 → 图库素材 → 怎么获取？」弹出的教程里写着：

> 两家都是**注册即给 Key、不用信用卡、可商用免署名**。任选一家填上就能用，
> **两家都填效果最好（一家没结果自动换另一家）**。

但代码里图源**只剩 Pexels 一家**（`cover/search.js:6-8` 明确记录 Wikimedia 国内超时、
Pixabay 不吃中文关键词，均已移除），面板里也只有一个 `#stock-pexels` 输入框。
教程正文的标题甚至已经改成「Pexels（唯一图源 · 支持中文搜索）」，但引导语没跟着改。

### 复现步骤
1. 打开页面 →「AI」→ 面板底部「怎么获取？」
2. 读第一段引导语

### 预期结果
引导语与面板一致：只讲 Pexels 一家。

### 实际结果
引导语仍写「两家都填效果最好（一家没结果自动换另一家）」，用户会去找第二家图源，
在面板里找不到对应输入框。

### 严重程度
**P3**。不影响功能，属于文案漂移；但会让用户困惑「第二家在哪」。

### 证据
- `pwa/index.html:111`（引导语）
- `pwa/src/cover/search.js:6-8, 137, 187`（代码事实：只剩 Pexels）
- `pwa/src/app.js:948` 注释「只存 pexels（Pixabay 已移除，2026-10-27）」

### 初步原因
2026-10-27 移除 Pixabay/Wikimedia 时，改了教程的**小标题**与**代码**，漏改**引导语**。

### 建议修复方向
把 `pwa/index.html:111` 那段改成单图源表述，例如：
「Pexels 注册即给 Key、不用信用卡、可商用免署名。填一个就能用，支持中文关键词。」

### 可能影响的其他功能
无。仅文案。

### 回归用例
`TC-DOC-03`

## BUG-03（P2）上传带文字的成品图会重叠，且无「用纯照片」提示

### 对应测试用例
`TC-COVER-11`（重叠）、`TC-COVER-12`（无提示）

### 问题描述
封面页「底图 → 上传」只提供一个「选择图片」按钮，**没有任何提示说明应该用什么样的图**。
用户（很自然会）上传一张「已经排好版的成品封面」时，产品会把标题文字直接叠在
底图原有的文字上，出现严重重叠与糊字。

这是产品定位问题：封面引擎的设计前提是「底图是一张照片」，但 UI 没把这个前提告诉用户。

### 复现步骤
1. 顶部「小红书标题图生成」→ 选任意版式
2. 「底图」→「上传」→ 选择一张**自带文字的成品图**（如 `pwa/dist/samples/cover-sample-editorial-dune.jpg`）
3. 点「保存大图」
4. 打开产出的 PNG

### 预期结果
要么给出可读结果，要么在上传时就提示「请用不带文字的纯照片作底图」。

### 实际结果
产出图上「周末去海边，我把手机调成了飞行模式」与底图自带的「封面 · COVER」条
和「周末去海边」重叠，副标题行出现糊字（两行文字压在一起）。

### 严重程度
**P2**。功能本身可用（用纯照片完全正常，见 `TC-COVER-08`），但默认用户会踩；
结果图不可用，用户会以为是产品坏了。

### 证据
- 重叠产物：首轮 `output/qa-story/bigtype-*.png`（用 samples 成品图当底图，470268B）
- 对照组：`output/qa-story/bigtype-*.png`（用 `public/images/01-old-photos.jpg` 纯照片，3051596B，完全正常，已目视）
- 无提示：`pwa/src/cover/index.js:378-388`（上传分支只有 `label.textContent = '选择图片'`）

### 初步原因
1. 上传分支缺少说明文案（`cover/index.js:378-388`，对比「纯色」分支有 `cv-hint` 说明）。
2. 更深一层：`analyze.js` 的底图可读性分析只测「文字区对比度」，
   **无法识别底图本身是否含文字**，所以也给不出「这张图不适合当底图」的判断。

### 建议修复方向
1. **低成本**：上传区补一句 `cv-hint`：「建议用不带文字的纯照片；带文字的成品图会和标题重叠。」
2. **中成本**：`analyze.js` 增加一个「底图文字密度」启发式（边缘密度/连通域数量），
   超过阈值时提示「这张图本身有文字，叠字会看不清，建议换一张」。
3. **不做也行**：如果判断成本过高，至少做第 1 条——用户看到提示就不会踩。

### 可能影响的其他功能
- 联网搜图（Pexels）不受影响：图库图基本都是纯照片。
- 「纯色」模式不受影响。

### 回归用例
`TC-COVER-11`、`TC-COVER-12`
