## 6. 验证方法：别再被 headless 512 骗了

**这是本轮踩到的、最容易让下一个人白干半天的坑：**

> Windows 版 headless Chrome **有最小窗宽 512px**。用 `--window-size=375,812` 截出来的「移动端」截图，`innerWidth` 其实是 **512**。
> 窄屏的溢出和重叠会被完全掩盖 —— 之前拿到图说「375 没问题」，实际是 512 下的图。

正确做法用仓库里新增的 `scripts/cdp_measure.mjs`（Node ≥22，**零依赖**，用内置 WebSocket，`playwright` 这个环境里没装）：

```
# 量原型
node scripts/cdp_measure.mjs file:///E:/test/wechatca2/docs/prototypes/xhs-studio-redesign.html 375 812 scripts/snippets/nav-375.js

# 量真实 dist（先把 dist 起起来）
cd pwa/dist && python -m http.server 8123 --bind 127.0.0.1
node scripts/cdp_measure.mjs http://127.0.0.1:8123/index.html 375 812 scripts/snippets/nav-375.js
```

它走 `Emulation.setDeviceMetricsOverride`，拿到的才是真的 375 CSS px。探针会输出：`scrollWidth` vs `innerWidth`、每个元素的 `L/R/W/H`、`top-left.R` 和 `top-right.L` 谁压谁、超宽元素清单。

其它几条验证纪律（都踩过）：
- **判据先看真实产物再定**，别拍脑袋写阈值（曾误报过 2 条）
- **目视判断必须在放大后做**，`--force-device-scale-factor=2`。缩略图会把强调色的数字看成蓝色、把正常渲染看成溢出
- headless 截图是**延迟写盘**，跑完要 `sleep 3-4` 再 `ls`
- **永远不要 `taskkill /IM chrome.exe`**（用户自己开着 30+ 个 Chrome 窗口）。脚本用独立 `--user-data-dir`，只 kill 自己起的进程

- **V6** 保存按钮 Tab 序早于构图切换 → ⚠️ **仍未修，需人评估**。2026-10-31 桌面 1440 复测确认现象属实：
  `#save` 是第 17 个可聚焦元素，六个构图按钮在第 19–24 个 —— 与验收标准 C18（输入→搜图→选图→换构图→保存）冲突。
  **但文档原来给的解法（「把 `#save` 移出 `.left`」）在网格布局下不成立**：`.wrap` 是
  `display:grid; grid-template-columns:minmax(370px,430px) 1fr` 两列，`#save` 在左栏 `.left` 内、构图在右栏 `.right` 内，
  **grid 列顺序 = DOM 顺序**，左栏任何元素都必然早于右栏构图。要让保存晚于构图，只能把它移出 `.left` 并置于右栏 DOM 之后，
  这会脱离两列结构（桌面保存按钮掉出左栏操作区）。CSS `order` 无效（`.left` 是 block 非 flex，且 order 不改 DOM/Tab 序），
  `tabindex` 正值为反模式。**三条路都要动桌面视觉结构，请人拍板。**
