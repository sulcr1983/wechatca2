## 0. 一句话

> **今天的 164 套主题里，只有 49 套是"长得不一样"，其余 115 套只是换了颜色。**
> 版式只有 8 种、长图文内页只有 5 种，所以再怎么加主题，用户看到的还是那几个样子。
> 修法不是继续加主题，而是**把"结构"从"颜色"里拆出来**，让结构和颜色可以自由组合。

## 1. 你说的三个问题，先看数据

### 1.1 「公众号排版风格版式太单调，很多模版就是改个颜色」

这句判断是准确的，而且可以量化。把每套主题的**设计手法**归一（丢掉具体色值和字号，只看"用了什么招"：标题有没有底色块 / 有没有下划线 / 有没有左竖条 / 居中还左对齐 / 引用是底块还是竖条 / 行距档位 / 衬线还是无衬线），164 套主题落成：

| 事实 | 实测值 |
|---|---|
| 主题总数 | 164 套 |
| **不同的「设计签名」** | **49 种** |
| 最大的同构组 | **17 套**（暮色族 10 套 + 墨笔 / 彩纸 / 序号等） |
| 次大的同构组 | **8 组，每组各 12 套**（公文 / 信笺 / 节庆 / 素页 / 夜航 / 钢印 各族全是同一个结构换色调） |
| 只有 1 套独有的签名 | 35 种 |

也就是说：**164 套里，有 129 套（79%）能找到"和它长得一模一样的兄弟"**。

再看两个最显眼的位置：

| 元素 | 分布 | 结论 |
|---|---|---|
| `h1`（文章大标题） | 居中无装饰 50 / 居中+下划线 34 / 左对齐+下划线 29 / 底色块 29 / 渐变 17 / 左竖条 8 | **113 / 164 = 69%** 是「居中」或「居中 + 一条下划线」 |
| `h2`（小标题） | 左竖条 48 / 无装饰 35 / 下划线 22 / 色块圆角 24 / 色块直角 12 | **105 / 164 = 64%** 是「左竖条 / 什么都没有 / 下划线」 |

族内更直白——同一族的 12 套，描述文本只换了颜色名：

```
公文·湖蓝：深色标题块层层收紧，虚线分节，湖蓝做贯穿始终的定位色。
公文·竹青：深色标题块层层收紧，虚线分节，竹青做贯穿始终的定位色。
公文·粉黛：深色标题块层层收紧，虚线分节，粉黛做贯穿始终的定位色。
```

### 1.2 「小红书的标题图还行，按最新的 html 原型图设计挺好」

同意。标题图那条线在 2026-11-01 的 V2 方案里已经重做过（`docs/design-xhs-studio-final.md`），
版式 × 色板两层模型、20 套三族配色、5 列一屏 16 套全见 —— **这条线不动**。
本方案只借它的模型去修另外两条线。

### 1.3 「小红书长图文的版式完全不够看，很单调」

这条比公众号更严重，原因很具体：

| 事实 | 实测值 |
|---|---|
| 长图文模板数 | 12 套（`cards.js` 的 `LONG_TPLS`） |
| **页面角色（排版骨架）数** | **5 种**：`opening` / `dense` / `points` / `quote` / `closing` |
| 12 套模板的差异在哪 | 页眉、页脚、纸纹、字体族、装饰（胶带 / 齿孔 / 星点…） |
| 正文区是否共用 | **共用**。12 套全部走 `@@S@@:where(.card .body p)` 这一条规则 |
| 内页能不能放图 | **不能**。`image` 只在 `role === 'cover'` 时传入 |

所以用户翻一套长图文时，**读到的是同一份排版，只是纸变了**。
12 套模板里风格规则最少的「极简留白」只有 2 条，「杂志编辑」4 条 —— 它几乎什么都没做。

## 2. 根因：结构被写死在代码里，主题只能改颜色

这不是"做得不用心"，是**架构上就长不出结构**：

```
主题 JSON 能表达的属性（穷举）
  font_size / color / font_family / line_height / letter_spacing
  text_align / padding / margin / border_* / background / border_radius

主题 JSON 表达不了的
  ✗ 章节之间怎么分隔（是不是有一条横贯线？还是缩进？还是留白？）
  ✗ 首屏放什么（期号？大编号？导语？署名？）
  ✗ 引用是大字还是底块还是侧栏
  ✗ 段落能不能成对并排
  ✗ 一张图能不能进内页
```

`core/format_engine.py` 的 `LAYOUT_REGISTRY` 只有 4 个真版式（`magazine` / `rhythm` / `cardflow` / `outline`），
加上 3 个老版式（`card` / `hero` / `timeline`），一共 7 条路径。
**新增版式要写 Python、要过 164 套渲染审计、要动门禁**，所以历史上加得很慢。

结论：**只要结构由代码硬编码，主题数再多也只是色卡。**

## 3. 方案：把「长相」拆成两层

### 3.1 核心决策

```
长 相 = 版式（结构，决定"骨架"）  ×  皮肤（颜色/字体，决定"气质"）

版式 Layout   8 → 13 种      决定：章节怎么分隔、首屏放什么、引用怎么处理、段落是否并排
皮肤 Skin    164 套不变      决定：底色、墨色、强调色、字体族、行距

组合数        13 × 164      而不是今天的「49 种 + 115 个重复」
```

**为什么拆两层，而不是再造 100 套主题？**

1. 组合数从「加法」变成「乘法」：加 5 个版式 = 多 820 种长相，写 5 个文件就够。
2. 用户的决策路径变短：先选"我要什么骨架"，再选"什么气质"。今天他要在 164 张卡里找，
   其中 115 张是重复的。
3. **兼容现状**：皮肤层就是今天的主题 JSON，一个字不用改。老用户的收藏、localStorage、
   全部 theme id 都不受影响。版式层是**新加的、可选的**，不选就是今天的样子。

### 3.2 关键约束（这条决定方案能不能落地）

> **版式必须零成本作用于所有 164 套皮肤。**

具体做法：版式不写死颜色，全部从 `theme.colors` 派生（与现有 `_inject_container_styles` /
`_resolve_band_bg` 同一套做法）。这条项目里已经验证过：容器样式从 `theme.colors` 派生后，
92 套主题的容器才"跟着各自色系走"，而不是全部长成同一套灰白。

反例（必须避免）：`_wrap_hero_sections` 曾经写死 `background-color:#ffffff`，
在 `su-deepwater` 这种暗底主题上直接白底浅字不可读。**任何版式里不许出现字面色值。**

## 4. 公众号排版：新增 5 个版式

新增版式的设计**不是自己编的** —— 全部来自仓库里已有的 `references/layout-recipes.md`
（M01–M16 / S01–S12，归藏设计系统的版式配方）。这符合项目既定纪律：
「不要自己设计页面，要去搜同类优秀设计抄过来」。V2 封面方案已经用过同一批配方。

| 版式 | 配方出处 | 结构（用户能看见的差别） | 适用内容 |
|---|---|---|---|
| **刊头版** `masthead` | M01 Magazine Issue Cover | 期号栏 + 栏目名 → 衬线大标题 → 斜体导语 → 署名行（作者 / 阅读时长）→ 章节号 + 标题；引用升级成**横贯整宽的斜体大字** | 特稿、人物、深度、周报 |
| **侧边栏** `marginal` | M11 Marginalia Essay | 左侧 64px 窄栏放**章节大编号 + 英文标签**，右侧正文用一条发丝竖线隔开；导语缩进对齐正文 | 行业观察、读书笔记、方法论 |
| **大编号** `bignum` | S09 KPI Tower / M12 Section Divider | 每节以 **44px 等宽大编号**开篇，上面一条横贯分隔线；清单条目带方形序号块 | 「5 个方法 / 3 个坑」这类结构化内容 |
| **双栏对照** `split` | M03 Editorial Essay Split / S02 Two Signals | 正文段落**成对并排**（微信兼容用 `table` 模拟，不能 `column-count`），中间发丝竖线；金句走整宽色带 | 正反 / 前后 / 优劣 / 对比评测 |
| **大字刊头** `bighead` | M13 Hero Question | 首屏只有一句话，字号拉到 32–36px 居中；正文从第二屏才开始 | 观点、金句、短文、宣言 |

> 原型里已经把这 4 个（刊头 / 侧边栏 / 大编号 / 双栏）和现状做了**同文案同皮肤**的 A/B 对照。
> 皮肤选「信笺·湖蓝」时，默认版式和刊头版的差别肉眼可见 —— 而这个差别**全部来自结构**。

### 4.1 老版式怎么处理

`theme.layout` 字段已经在 2026-10-29 全部清空（164 套都是"默认"），这是对的。
**新方案不改这个决定**：版式由用户在版式条里主动选，不写回主题 JSON。

版式选择记在 `supersu.layout`（localStorage），与主题分开存 —— 这样"换皮肤不丢版式、
换版式不丢皮肤"才成立。

## 5. 小红书长图文：页面角色 5 → 10

长图文的病根不是"模板少"，是"页面角色少"。5 种角色里 `dense` 一个就承担了 80% 的页数。

| 新增角色 | 结构 | 触发条件（自动识别，不用用户点） |
|---|---|---|
| **目录页** `toc` | 章节导航 + 页码 | 文章 ≥ 3 个小节且预计页数 ≥ 6 |
| **图文页** `photo` | 上半屏真图当证据，下半屏短标题 + 一句说明 | 该段有配图（见 §6） |
| **双栏论证页** `split` | 标题压顶 + 两栏对照（正反 / 前后） | 该段有两组并列短段落 |
| **编号塔** `ledger` | 大编号 + 短条目逐行，行间细线 | 该段是一个 ≥ 3 条的清单 |
| **数据页** `stat` | 超大数字当主视觉 + 一行说明 + 进度线 | 段首出现「87%」「3 倍」「第 5 名」这类数字断言 |

这 5 种在原型里已经排成一套完整长图文（P01 目录 → P02 正文 → P03 图文 → P04 双栏 → P05 编号塔 → P06 数据），
可以直接看"翻页时页面是不是真的在变"。

### 5.1 必须同时改的一条

`pwa/src/cover/cards.js` 的 `palOf(k)` 现在是**读全局 `state.pal`**，不是读传入的 `o.pal`。
这是本项目**已犯 6 次**的同一个 bug（见 `HANDOFF.md` §7.4）。加新角色时如果不先把
渲染函数改成**显式入参**，新角色必然全同色 —— 这会是第七次。

> 落地顺序上，这一条排在新增角色**之前**，不是之后。

## 6. 自动配图：能做什么、不能做什么

你提的需求是：**「标题图那边已经填了搜图的 Key，公众号排版这边能不能按上下文自动配图」**。

能。但有一个**平台硬约束必须先说清楚**，否则做出来就是"看着有图、贴过去没图"。

### 6.1 硬约束（这不是我们偷懒，是微信的限制）

代码里已经写死了这条事实（`pwa/src/app.js` 顶部注释 + `toastAfterCopy()`）：

> 微信公众号编辑器粘贴富文本时**只认公众号图床 URL，拒绝 `data:` URI，外链图也不显示**。

所以：

| 使用场景 | 自动配图是否生效 |
|---|---|
| 导出 HTML（自包含） | ✅ 完全生效 |
| 导出长图 PNG | ✅ 完全生效 |
| 离线留档 / 本地预览 | ✅ 完全生效 |
| **复制到公众号后台粘贴** | ❌ **图片不显示**，用户必须在素材库手动上传 |

**结论：不做「自动插图到正文」，做「配图建议条 + 一键下载」。**

理由：自动插图会让用户以为"复制过去就好了"，粘贴完发现图全丢了 —— 这正是
`toastAfterCopy()` 现在要专门提醒的错误。做了自动插图，等于亲手制造这个坑。

### 6.2 实际形态（诚实、可落地）

```
┌─ 解析条下方新增一条「配图建议」───────────────────────────────┐
│  ✦ 已为本篇找到 3 处建议配图（来自 Pexels）                    │
│                                                              │
│  ①  第 1 节「先想清楚写给谁」   [缩略图] 办公室 / 笔记本     │
│  ②  第 3 节「把重复劳动交给工具」[缩略图] 键盘 / 效率工具     │
│  ③  结尾                           [缩略图] 日落 / 城市剪影  │
│                                                              │
│  [全部下载 3 张]  [插入正文（导出用）]  [换一批]  [关掉]      │
│                                                              │
│  ⓘ 公众号后台不认外链图和内嵌图。下载后请到「素材库 → 图片」    │
│    上传，再在正文里插入。                                     │
└──────────────────────────────────────────────────────────────┘
```

三个动作的语义必须分开，不许混：

- **全部下载**：打包 3 张 PNG（复用已有 `fflate`，`export.js` 的图片 ZIP 逻辑），用户拿去上传素材库。
- **插入正文（导出用）**：把图内嵌进 HTML，**只对导出 HTML / 长图生效**，按钮上要写「导出用」。
- **换一批**：Pexels 翻页（`search.js` 已支持 `page` 参数）。

### 6.3 AI 要不要参与？—— 要，但只做一件事

「自动识别上下文」有两种做法，我们只用后一种：

| 做法 | 评价 |
|---|---|
| AI 生成图片（文生图） | ❌ 不做。项目没这个能力（`image_gen.py` 已随 Flask 版归档删除），且要第二个 Key |
| **AI 只输出「插图位置 + 英文关键词」，图由 Pexels 搜** | ✅ 做。与项目既定的「AI 不改正文」契约完全一致 |

具体契约（照抄 `planStructure` 的做法，`ai.js` 里已有同款）：

```jsonc
// AI 输入：全文文本   输出：只此一个 JSON，不含任何正文
{ "spots": [
    { "para": 3, "why": "章节开头，需要一个场景图", "kw": "office desk laptop morning" },
    { "para": 11, "why": "讲效率工具", "kw": "mechanical keyboard closeup" }
] }
```

- 中文关键词不能直接喂 Pexels（`search.js` 的 `guessQuery` 有内置词表兜底，但覆盖有限），
  所以让 AI 直接出**英文关键词**，命中率高得多。
- 越界 / 段落号不存在 / 关键词为空 → 那一处直接忽略，**不影响正文一个字**。
- 没配 AI → 走本地规则（按 h2 标题分词 + `guessQuery` 词表），质量差一些但仍然可用，**不静默失败**。

### 6.4 Key 复用

搜图的 Key 已经存在 `localStorage['supersu.cover.stock.v1'].pexels`（`search.js` 的 `STOCK_KEY`）。
**公众号页直接读同一个键，不新建存储、不让用户再填一次。**

但要注意 `HANDOFF.md` §7.5 记的债务：`supersu.*` 共 18 个键散在 5 个模块、没有注册表，
`clearAll()` 只手写清了 5 个。这一轮既然要碰存储键，**顺手把注册表建了**，否则就是第 19 个漏网的。

### 6.5 还要补一个参数

`search.js` 的 Pexels 请求写死 `orientation: 'portrait'`（竖图，为封面服务）。
公众号正文插图要的是**横图**，必须加参数（`landscape`），不能共用。

## 7. 落地顺序（每步都能单独回滚）

| 顺序 | 动什么 | 为什么排这里 | 风险 |
|---|---|---|---|

| **2** | `core/format_engine.py`：新增 `LAYOUT_REGISTRY` 里 5 个版式 | 纯新增函数，不动既有 4 个；每个都做「正文零丢失」断言 | 中 |
| **3** | `pwa/src/app.js` + `style.css`：版式条 8 → 13 个胶囊，选择存 `supersu.layout` | 纯前端，可选，不选就是现状 | 低 |

### 7.1 必须补的两条产物级断言（不许省）

`HANDOFF.md` §7.2 记着本项目最大的系统性盲区：**断言停在「按钮可用了 / toast 出现了」**。
所以这一轮至少要补：

1. **版式真的不一样**：同一篇夹具 × 同一个皮肤，跑两个版式，导出的 HTML **结构指纹必须不同**
   （不是比像素，是比 `<h2>` 前面的兄弟节点结构）。反向验证：把版式函数换成 identity，这条必须失败。
2. **自动配图真的定位对了**：给一篇 12 段的夹具，断言返回的 `spots[].para` 全部落在 `[0, 12)`，
   且**每一处的插图位置对应的原文段落文本能对上**（不是只看"返回了 3 条"）。

第 2 条特别重要：`planStructure` 那套「越界/重叠一律忽略」的逻辑，如果只测"返回了 JSON"
是测不出错位的。

## 8. 原型怎么看

```bash
# 仓库根起服务（或在文件管理器里直接双击）
python -m http.server 8127
# http://127.0.0.1:8127/docs/prototypes/layout-system.html
```

原型里有三个开关：

1. **顶栏「公众号排版 / 小红书长图文」** —— 两条线分开看
2. **左栏 5 个皮肤** —— 从这里提炼的真实主题色（信笺·湖蓝 / 公文·湖蓝 / 夜航·湖蓝 / 墨韵 / 节庆·麦金）。
   换皮肤时**结构完全不动** —— 这是为了让你亲眼看到"今天 164 套主题的差别就停在这一步"
3. **右栏版式卡** —— 每张卡左侧那个小竖条是**结构示意图**，不是缩略图

> 设计上参考了「句方便」（seneasy.cloud）的「选择排版主题」弹窗：
> 卡片 = 顶部名称 + 族标签 + 一句话描述 + **真的会渲染的迷你预览** + 底部收藏。
> 那个预览花的那点算力是值得的 —— 用户选的是"长什么样"，不是"叫什么名字"。
> 完整的三栏主题选择器见 `docs/prototypes/theme-picker-seneasy-style.html`（164 套真实主题数据内嵌，197KB 自包含）。
